The direction mostly holds. What changes it is what the live code shows:

1. **A display change closes Vision.** Any display-topology change (a monitor sleeping, a dock, a resolution change) makes Vision exit, and nothing relaunches it (`main.cpp:1004`). Monitor sleep/wake has never been tested. Handling these changes without exiting should be part of the refactor, because it decides how long the new capture and view objects live. At 3–4 monitors this gets worse.
2. **No low-vision user or assessor has used Vision on a real task yet.** A small session comparing Context + Detail with full-screen magnification can run now on the current alpha, alongside the refactor. It shouldn't wait until Stage 6.
3. **The proposed pieces miss the one that holds today's coupling: a workspace coordinator.** The per-frame loop in `render_loop` plus the process-wide settings globals is that coordinator. Monitor-crossing ownership belongs there as policy state: one active view, handed over by the user's latest pointer or typing activity, routed by screen geometry. It doesn't need to be its own subsystem.
4. **Two current defects make the refactor worth doing.**
   - Pointer positions off the source monitor are thrown away when sampled. That switches off the existing "pointer moved last" guard, which is the likely root cause of the known Detail jump.
   - Highlights are only drawn for whatever the view is following. So the caret highlight can't show while caret following is off, which contradicts the README's claim that the two are independent.
5. **Same-monitor magnification is not proven.** The single-monitor fallback is a 45%-size window; it only shows that capture exclusion works. Full-screen self-magnification still has open problems with clicks, a doubled cursor, and staying above Start and Alt+Tab. The project's own 2026-09-19 review asked for a separate test of this, and it never ran. That test is the top-ranked experiment before Stage 3.
6. **The text-quality comparison used the weakest possible Vision baseline.** Vision scales with plain bilinear filtering in a single shader pass, so "softer than ZoomText at 4x" doesn't show what raster scaling can achieve. The first renderer step is a cheap offline comparison of scaling filters, with ClearType on and off, and it can run in parallel with the refactor. The xFont verdict came from one person partly using phone photos, so text re-rendering stays an open option, not a rejected one.
7. **First-product gaps the plan misses or underrates:**
   - Detail shows a crosshair, not the real pointer shape (arrow, I-beam, hand).
   - Zoom stops at 4x.
   - Vision's own settings and help windows use fixed pixel fonts and layouts, so they won't scale with Windows display scaling.
   - The Ctrl+Alt hotkeys very likely fire on AltGr characters on European keyboards; for example German AltGr+Q ("@") would exit Vision. This needs a 10-minute check.
   - There is no start-at-sign-in option.
   - Windows Magnifier, the free baseline, is missing from the comparison set.
8. **A smaller product doesn't buy a proportionally smaller support burden.** Keeping tracking and capture working across Windows, Office, browser and driver updates costs about the same regardless of feature count. The real saving is not hooking into applications, which is the strongest argument for keeping text re-rendering and Tethered-style features narrow.

Decisions: keep the shared GPU device (behind an explicit object), per-view state, the overlay/motion split and the narrow scope. Modify the architecture decomposition, the crossing policy, the renderer's first step and the localisation timing. Reject shutting down on topology changes and reserving a seam for Tethered-style relocation. Same-monitor magnification and a one-monitor lens mode need more evidence.

None of the open product questions blocks the first behaviour-preserving refactor steps; the only prerequisite is a replay test that proves behaviour is unchanged. The display-lifecycle, monitor-identity and same-monitor tests gate the later steps.
