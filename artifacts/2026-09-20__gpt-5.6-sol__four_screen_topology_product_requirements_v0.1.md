# Visual — Four-screen Doxa topology: product and architecture requirements v0.1

**Date:** 2026-09-20  
**Project:** Visual / Doxa  
**Status:** product assumption to carry into future architecture, spikes and testing

## Product assumption

The normal Doxa deployment should be treated as **four active Windows displays**:

- the laptop's built-in display;
- three external Doxa displays.

A two-display setup remains a useful minimum engineering configuration, but it is no longer the representative product topology.

## Architecture consequence

The principal architectural discontinuity is still the move from one display to multiple independent displays. If Visual is built around:

**Source -> Point of Interest -> View transformation -> Destination**

rather than hard-coded `primary` / `secondary` logic, the move from two to four displays is mainly a scaling, topology and product-policy problem rather than a redesign of the capture/render core.

Requirements from now on:

- no feature may assume exactly two monitors unless explicitly scoped as a spike;
- source and destination must be independently selectable;
- one source may feed several views;
- several destinations may hold independent visual state;
- monitor identity must be persistent and role-based rather than Windows monitor-number based;
- topology changes (dock/undock, sleep, reconnect, primary changes) are normal recovery paths;
- coordinate handling must support negative coordinates, mixed DPI, different refresh rates/resolutions and arbitrary physical arrangements;
- performance tests must eventually include four active displays and multiple simultaneous Visual views.

## Product principle

Four displays should not become four dynamic magnified surfaces competing for attention.

The strongest Doxa hypothesis remains **stable physical roles**: one active task can change while the other displays preserve context, reference or communication state.

A credible default four-screen role set is:

1. **Work** — active application/task;
2. **Detail** — magnified/inspection view driven by pointer/caret/focus policy;
3. **Context / Reference** — stable overview, document, dashboard or fixed reference;
4. **Communication / Control** — email/chat/meeting/status/settings, often suitable for the laptop panel.

These are roles, not fixed physical assignments. For severe low vision the laptop panel may be a poor primary reading surface, so role assignment must be configurable and should eventually be learnable from user workflow.

## Features whose importance rises materially at four displays

### 1. Monitor Roles and persistent identity — core

Visual must let users think in names such as Work, Detail, Reference and Communication instead of Monitor 1/2/3/4.

Roles should survive:

- reboot;
- docking/undocking;
- cable reconnect;
- Windows changing monitor numbers;
- primary-display changes;
- identical Doxa panel models where possible.

### 2. Independent per-screen visual state — core

Each destination should be able to retain its own:

- zoom level;
- contrast/color treatment;
- follow policy;
- frozen/live state;
- pointer/caret/focus locator behavior;
- source assignment.

Global magnification state becomes increasingly inappropriate with four displays.

### 3. Fast source-to-role routing — core

A user should be able to send what matters to a role without dragging windows or configuring coordinates.

Examples:

- inspect current pointer target on Detail;
- send current app to Work;
- freeze current region on Reference;
- move current application to another role;
- return exactly to prior state.

### 4. Pointer/find/move across four displays — core

Four surfaces increase pointer travel and loss risk.

Visual should investigate:

- strong Find My Pointer;
- one-command jump to a named role;
- optional pointer warp to active POI;
- visible transition cue when pointer crosses monitors;
- edge behavior that reduces accidental overshoot without trapping the user.

### 5. Stable-context linking — high value

If Detail magnifies an area originating on Work or Context, the source display should be able to show a subtle locator corresponding to the Detail region without moving the source view.

The relationship should remain visually understandable: "this Detail view comes from here."

### 6. Workspace/role restoration — high value

Four displays make manual reconstruction expensive.

Visual should restore, best-effort:

- application-to-role placement;
- Visual view state per role;
- zoom/effects/follow policy;
- fixed references;
- last useful source/destination mapping.

Restoration must degrade gracefully when a monitor or application is unavailable.

### 7. Topology recovery / graceful degradation — core

If the laptop is disconnected from Doxa, one Doxa panel disappears, or the user undocks:

- Visual must not lose state catastrophically;
- roles should be temporarily remapped or suspended;
- inaccessible windows should be recovered to visible displays;
- reconnect should restore the intended role map where confidence is high.

### 8. Attention management — four-screen-specific UX concern

Four displays create a new accessibility failure mode: too many things move at once.

Default policy should favour:

- one active/dynamic Detail surface;
- stable supporting surfaces;
- explicit user-visible role changes;
- minimal automatic cross-screen movement;
- optional attention cues rather than constant animation.

### 9. Performance scheduling — engineering requirement

Four displays do not imply four full-rate capture/render pipelines.

Visual should support:

- shared capture source when multiple views originate from one source;
- low/update-on-change cadence for static context/reference surfaces;
- retained textures for frozen references;
- high cadence only for active Detail/Work views;
- explicit measurement of cross-adapter and USB-display behavior.

### 10. Presentation/privacy roles — useful later

With four screens, private/public separation becomes substantially easier:

- private magnified Detail;
- normal public/share output;
- notes/reference;
- meeting/chat/control.

Visual should eventually expose clearly which display is intended for screen sharing and which contains private accessibility state.

## Four-screen workflow concepts to test

### Low-vision productivity

- Work + Detail + Context + Reference
- Work + Detail + Reference + Communication
- Detail + Context + Secondary Work + Communication

### Meetings/presentation

- Private Detail + Public Output + Notes + Participants/Chat

### Spreadsheet/research-heavy

- Active sheet/work + magnified active range + stable sheet/context + source/reference document

### Mild-vision/general productivity

- Work + Reference + Communication + temporary Detail/Inspect

## Testing implications

Two-screen Spike 1 remains valid because it proves the first independent cross-monitor capture/render relationship.

After that, testing should expand in stages:

1. one source -> one Detail destination;
2. one source -> two destinations;
3. two independent source/destination relationships;
4. four active physical displays with mixed roles;
5. hot-plug/remove/reconnect one display during operation;
6. mixed DPI/resolution/refresh and laptop/external placement;
7. multiple GPU/USB-display paths when Doxa hardware is available.

The success criterion is not merely "Visual renders on four monitors". It is that roles remain understandable, stable and recoverable while the user can always identify where work, detail and context are located.
