# Vision development plan v0.5 — post Opus/Astra review

**Date:** 2026-09-30  
**Status:** executable development plan after independent Opus 5.5 xhigh + GPT-6 Astra xhigh review; implementation not yet started  
**Operational truth:** live repo + current acceptance evidence; preserve all pre-existing dirty/uncommitted work.

## 1. Objective

Generalise the current validated two-screen Vision runtime into a recoverable multi-view foundation **without jumping directly to feature breadth**.

The next milestone is not “support four monitors”. It is:

> Extract the current one-source / one-Detail relationship into explicit, testable responsibilities that preserve current behaviour, define geometry correctly, survive topology lifecycle changes, and can then be scaled to additional views without duplicating evidence/capture policy.

## 2. Review decisions now treated as programme constraints

The Opus/Astra reconciliation establishes:

- Keep WGC/D3D11 as the default graphics path.
- Model GPU ownership explicitly as a **device domain**; start with one domain.
- Shared evidence acquisition must publish evidence, not movement decisions.
- Add a **WorkspaceCoordinator** responsible for resolved workspace, movement ownership, routing, arbitration, command targeting and topology rebuild policy.
- Keep per-view state explicit.
- Use one movement owner initially; preserve manual override/switch.
- Visibility overlays and follow/movement are separate concerns.
- Saved workspace intent and resolved current topology are separate.
- Same-monitor interactive magnification is unproven and capability-gated.
- Display topology changes must eventually reconcile in-process rather than terminate Vision.
- Geometry/magnification semantics must be explicit before unequal source/destination layouts are generalised.
- Improve raster reconstruction before considering semantic text work.
- Start low-vision/assessor evidence early and in parallel.
- Windows Magnifier is part of the comparator set.

## 4. Gate 0A — trustworthy baseline/replay oracle

### Purpose

Make “behaviour-preserving refactor” objectively testable before moving responsibilities.

### Deliverable

Add a deterministic replay fixture around the current evidence -> arbitration -> viewport/locator path.

The replay record should contain enough to reproduce decisions without live UIA/WGC timing:

- frame/timestamp;
- source physical bounds;
- zoom and current viewport;
- pointer/caret/focus candidate presence, geometry, provider/source and freshness/activity timestamps;
- follow and locator visibility settings;
- selected movement candidate;
- resulting viewport;
- resulting locator/visibility output;
- temporary-normal/return state where applicable.

### Initial golden scenarios

At minimum:

- pointer tracking within source;
- caret tracking;
- focus tracking;
- pointer crossing/leaving source;
- pointer-vs-caret arbitration near the known boundary-jump case;
- follow disabled while locator visibility remains enabled;
- exact temporary 1x / return.

Known defects may be represented as **known-current behaviour** during structural slices. Their expected output changes only in a separately named policy slice.

### Exit criteria

- replay produces deterministic identical decisions from the same recorded input;
- a deliberate perturbation causes the oracle to fail;
- current acceptance raw evidence can seed at least one replay fixture;
- replay is fast enough to run on every structural slice.

### Rollback boundary

This gate adds test/telemetry infrastructure only. No runtime behaviour change is permitted.


## 5. Gate 0B — explicit geometry and magnification contract

### Problem

Current behaviour effectively assumes source and destination geometry are close enough that:

`source_crop = source_size / zoom`

can then be stretched across the destination.

That works acceptably for the current matched-screen case but is not a valid general definition of magnification for unequal resolutions, portrait destinations or partial-screen outputs.

### Contract to freeze before generalisation

Use **physical source pixels** and **physical destination pixels** as the base rendering geometry.

For a destination rectangle `D = (Dw, Dh)` and magnification `z`:

- the intended live source viewport size is approximately `(Dw / z, Dh / z)` source pixels;
- X and Y scale must remain equal unless an explicit non-uniform transform is introduced later;
- the viewport keeps the destination aspect ratio;
- POI/viewport policy remains in source physical coordinates;
- DPI/logical coordinates are converted explicitly at API boundaries;
- `zoom = 1x` means one source pixel maps to one destination pixel where possible;
- “show the whole source” is a separate **overview/fit** operation, not another definition of 1x;
- when the requested crop cannot fit inside the source, behaviour is explicit: clamp and letterbox/pillarbox rather than silently stretch non-uniformly;
- temporary normal/return stores enough state to restore the exact prior crop/zoom when topology remains compatible;
- topology changes may require a deterministic clamp/re-resolution rather than claiming exact restoration.

### Table-driven contract cases

Before runtime implementation, add pure geometry cases covering at least:

1. 1920x1080 source -> 1920x1080 destination at 1x/2x/4x;
2. 1920x1080 source -> 1280x720 destination;
3. 1280x720 source -> 1920x1080 destination;
4. 1920x1080 source -> 1080x1920 portrait destination;
5. partial destination rectangle;
6. negative virtual-desktop origins;
7. mixed DPI where physical monitor geometry is unchanged;
8. POI near each source edge;
9. exact return after temporary normal;
10. source resize while a view is active.

### Compatibility rule

The current validated matched-screen two-monitor behaviour must remain pixel-equivalent during the structural extraction. The generalized geometry contract can be introduced behind tests first and deliberately activated later for mismatched layouts.

### Exit criteria

- a short written geometry spec exists in the repo;
- pure tests express the cases above;
- “2x” has one unambiguous source-to-destination meaning;
- overview/fit semantics are separate from zoom semantics;
- no runtime code has yet changed visible behaviour.

## 6. Structural Slice 1 — explicit current View identity and runtime state

### Objective

Remove the first layer of process-global coupling without changing how the product behaves.

### Scope

Introduce one explicit current view object/state representing today's Detail relationship.

It should own, or provide access to:

- stable `ViewId`;
- current zoom;
- follow-pointer / follow-caret / follow-focus state;
- visual mode / colour parameters;
- locator visibility/style state;
- current viewport / return state;
- source binding and destination binding references;
- command targeting for view-scoped hotkeys.

Do **not** add multiple views yet. Do **not** change hotkey semantics. Do **not** fix the boundary jump or overlay/follow coupling in this slice.

### Tests to add/update

- current settings map into the one View state;
- hotkeys still affect that same single view;
- temporary 1x/return state is view-owned and exact;
- persistence round-trip remains unchanged;
- replay output is identical to Gate 0A golden fixtures.

### Acceptance

- Release build passes;
- 11/11 CTests;
- two-screen acceptance 8/8;
- replay equality;
- exact return remains 0 px delta;
- no user-visible feature change.

### Rollback boundary

The new state object can be removed without touching capture, evidence providers or rendering.

## 7. Structural Slice 2 — EvidenceSampler extraction with legacy routing preserved

### Objective

Stop evidence acquisition from being owned by the capture/render relationship.

### Scope

Create a global/shared `EvidenceSampler` that samples pointer, caret, focus and provider metadata once per tick and publishes an immutable snapshot.

The sampler should **not** decide:

- which view may move;
- which source the candidate belongs to;
- whether a candidate wins arbitration;
- whether an overlay is visible.

During this slice, preserve today's effective behaviour with a legacy routing/filtering adapter so replay results remain identical.

### Snapshot requirements

Each candidate should carry enough data for later routing:

- provider/type;
- geometry/anchor in explicit coordinate space;
- observed timestamp;
- activity/freshness timestamp or generation;
- process/window identity where available;
- validity/presence;
- topology generation.

Pointer evidence should not be destroyed merely because it falls outside the current source; source relevance is a later routing decision.

### Acceptance

Same as Slice 1, plus:

- sampling occurs once per frame/tick regardless of future view count;
- replay can consume recorded snapshots without live UIA/Win32 providers;
- provider failure/missing evidence is represented explicitly rather than converted into a movement decision.

### Behaviour note

If preserving legacy replay requires a temporary compatibility adapter that reproduces the old source filter, keep it. The known pointer-leave bug is corrected only in the later named policy slice.


## 8. Structural Slice 3 — pure view-update step

### Objective

Separate “what should this view show next?” from capture callbacks and presentation.

### Scope

Create a pure or near-pure update step that consumes:

- resolved source geometry;
- current View state;
- routed evidence snapshot;
- current manual/return mode;
- elapsed time / freshness state;

and produces:

- next viewport/crop;
- selected movement target/reason;
- overlay visibility/geometry intent;
- telemetry decision state.

The update step must not:

- sample UIA/Win32;
- own WGC;
- call Present;
- resolve physical monitor identity;
- mutate global settings.

Initially preserve today's arbitration/follow/locator semantics exactly through the compatibility path.

### Acceptance

- all Gate 0A replay fixtures run directly against this update step;
- current crop trajectories remain identical for matched-screen scenarios;
- temporary 1x/return remains exact;
- two-screen acceptance remains 8/8;
- no runtime behaviour change.

### Rollback boundary

The old inline update loop can be restored without changing capture or output objects.

## 9. Structural Slice 4 — explicit GPU domain, CaptureSource and OutputPresenter

### Objective

Separate graphics lifetime and scheduling so one future slow/occluded output cannot become the clock for capture/evidence/other outputs.

### Initial model

- `GpuDeviceDomain`: one D3D11/WinRT device domain initially; explicit object, not permanent process-global invariant.
- `CaptureSource`: one WGC source, latest owned/cached frame, frame generation/age, lifecycle state.
- `OutputPresenter`: destination window/swap chain/present resources.
- `ViewRenderer`: reconstruction -> colour -> overlay composition.

### Required changes

- stop treating a View as owner of the capture session;
- make source frame ownership explicit;
- stop holding the graphics/context mutex across blocking `Present`;
- add frame/source generation and age to telemetry;
- preserve current bilinear reconstruction in this structural slice;
- preserve current single output only.

### Tests

- one CaptureSource can publish frames independently of viewport decisions;
- an OutputPresenter can be destroyed/recreated without destroying unrelated policy state;
- stale/closed source state is explicit;
- frame generation is monotonic;
- a deliberately delayed presentation does not block evidence sampling in a unit/integration harness;
- current two-screen visual output remains unchanged for the qualified geometry.

### Acceptance

Canonical suite + replay equality + zero unexpected Present failures.

### Rollback boundary

This slice is allowed to change internal pacing/locking but not visible policy. If timing changes materially, retain before/after telemetry and revert if acceptance cannot explain the delta.

## 10. Structural Slice 5 — WorkspaceCoordinator with one ViewSession

### Objective

Make the object that owns today's hidden global coordination explicit before creating a second view.

### WorkspaceCoordinator owns

- resolved current workspace;
- list of ViewSessions (length = 1 in this slice);
- selected/active command target;
- movement-owner state;
- evidence routing;
- arbitration invocation;
- manual-mode/return suppression;
- topology generation reference;
- command targeting;
- telemetry IDs/reasons;
- rebuild request orchestration.

### ViewSession owns

- `ViewId`;
- source binding;
- destination binding;
- View state;
- viewport/return state;
- overlay state;
- OutputPresenter reference.

### Explicit non-ownership

WorkspaceCoordinator does not own WGC pixels or D3D device internals.  
ViewSession does not sample evidence or decide workspace ownership transfer.  
EvidenceSampler does not decide movement.

### Acceptance

- exactly one ViewSession reproduces the current product;
- every telemetry frame can identify workspace/view/source/topology generation;
- hotkeys resolve to the one active view without changing behaviour;
- replay and two-screen acceptance remain green.

### Architectural checkpoint

After Slice 5, stop and review the actual code before adding a second output.

The architecture should now be able to answer clearly:

- where evidence is sampled;
- where evidence is routed;
- where movement permission is decided;
- where viewport state lives;
- where capture lifetime lives;
- where presentation lifetime lives;
- where display topology state lives or will plug in.

If any answer is “multiple places”, do not proceed to multi-view yet.


## 11. Slice 6 — MonitorRegistry, topology generations and intended-vs-resolved workspace

### Objective

Stop treating the current monitor set as a startup-only fact.

### MonitorRegistry responsibilities

- enumerate current displays using stable Windows display APIs;
- produce a `TopologySnapshot`;
- assign a monotonically increasing topology generation;
- expose geometry, DPI, orientation and identity hints;
- diff old/new snapshots;
- debounce topology transitions.

### Persistent intent vs runtime resolution

Persist what the user intended:

- logical display bindings;
- workspace/view IDs;
- role labels;
- source/destination relationship;
- view settings.

Resolve that against the current topology at runtime.

Do **not** erase or rewrite the saved intent merely because:

- a monitor is asleep;
- a dock is absent;
- a display is temporarily disconnected;
- resolution/orientation changed;
- a fallback layout was used.

### Identity experiment gate

Before freezing the durable display-key format, run a small identity probe across:

- reboot;
- unplug/replug;
- port swap;
- primary-display change;
- at least two identical/near-identical panels if available later.

Use `QueryDisplayConfig` target/path information plus hardware metadata where available. Geometry is supporting evidence, not silent identity truth.

### Acceptance

- current two-screen intent resolves identically;
- missing display produces an explicit unresolved/safe fallback state;
- saved settings survive temporary topology loss unchanged;
- telemetry includes topology generation and binding confidence;
- no multi-view breadth yet.

## 12. Slice 7 — in-process topology reconciliation

### Objective

Replace the current long-term model of “topology changed -> terminate Vision” with a debounced workspace rebuild.

### Initial recovery strategy

Prefer a **whole-workspace rebuild** on settled topology change over premature surgical recovery.

Sequence:

1. detect topology change;
2. mark current generation stale;
3. pause movement/presentation decisions that depend on old geometry;
4. debounce until topology settles;
5. resolve saved intent against the new snapshot;
6. tear down invalid sources/outputs;
7. rebuild required CaptureSources/OutputPresenters/ViewSessions;
8. resume with a new topology generation;
9. surface an explicit user message only if binding is ambiguous or a requested role cannot be restored.

### Physical acceptance scenarios

At minimum:

- HDMI/DP unplug and reconnect;
- monitor sleep/wake;
- resolution change;
- DPI/scaling change;
- primary-display change;
- lock/unlock.

RDP/UAC/secure desktop remain separate support-boundary questions and should not silently expand this slice.

### Exit criteria

- Vision does not terminate merely because `WM_DISPLAYCHANGE` occurs;
- current supported workspace returns after reconnect/sleep where identity is unambiguous;
- no stale frame/evidence from the old topology generation can move the new workspace;
- ambiguous identity never silently reassigns Detail to the wrong physical screen.

## 13. Slice 8 — first scaling proof: one source -> two outputs

### Objective

Prove source reuse and independent output state before adding a second captured source.

### Scope

Behind an engineering flag, create two ViewSessions that consume the **same CaptureSource** and present to two destinations or test surfaces.

Each view must have independent:

- zoom;
- viewport;
- colour/visual state;
- overlay state;
- present cadence/state.

### What this decides

- whether one device domain and one frame cache are sufficient for the qualified case;
- whether a slow/occluded output interferes with another;
- whether source-frame ownership is correct;
- whether per-view state is genuinely isolated.

### Acceptance

- source is captured once;
- two outputs can present independently;
- delaying/occluding one output does not stall source acquisition/evidence/other output;
- changing zoom/colour in one view does not alter the other;
- telemetry attributes frame/view/source correctly;
- current default product remains one Detail output unless the flag is enabled.

### Stop condition

If fan-out requires hidden copies, locks or present coupling that violate the architecture invariants, stop before adding a second source.

## 14. Slice 9 — second source + generic N-view runtime

### Objective

Add the first truly multi-source case only after fan-out works.

### Scope

- second CaptureSource;
- second ViewSession bound to that source;
- generic collections rather than primary/secondary special cases;
- no automatic ownership transfer yet beyond a simple explicit selected view;
- workspace schema upgraded only as needed to represent the actual implemented case.

### Acceptance

- two sources and two views operate without duplicate evidence sampling;
- closing one source suspends only dependent views;
- one view/source failure does not corrupt another's state;
- command targeting is explicit;
- current Context + Detail preset remains expressible as one normal workspace configuration.

## 15. Policy Slice P1 — active movement owner and pointer-leave hold

This is the first intentional interaction-policy change after structural extraction.

### Initial policy

- one movement owner per workspace;
- explicit view selection always wins;
- pointer activity on an eligible **source** may select its associated view;
- entering a passive Detail output does not automatically rebind that view to itself;
- on pointer leave, retain the current viewport and pointer-intent barrier;
- semantic evidence observed before the leave cannot suddenly regain control;
- credible new caret/focus activity in another eligible source may transfer ownership;
- zoom/colour/follow commands target the selected view;
- emergency suspend/exit remain workspace-wide.

### Acceptance additions

Add explicit replay/physical scenarios for:

- pointer leave with fresh caret evidence;
- pointer return;
- typing/focus transfer to another source;
- explicit manual switch;
- inactive view remains stable;
- no simultaneous unintended panning.

## 16. Policy Slice P2 — decouple overlays from following

### Objective

Allow target visibility without forcing the viewport to follow that target.

Examples that must become valid:

- caret locator visible while caret following is off;
- pointer cue visible in a static Context;
- focus frame visible in an inactive view when the target is inside its viewport.

### Model

Each target type should carry separately:

- current validity/presence;
- geometry;
- observed/activity timestamps;
- style/preset;
- display policy;
- follow eligibility.

### Acceptance

- existing follow behaviour remains unchanged unless enabled;
- overlay-only scenarios replay deterministically;
- overlay size is tied to destination presentation units, not magnified source pixels;
- duplicate native/captured/custom pointer representation is explicitly prevented.


## 17. Parallel workstreams that should not block the first extraction

### A. Raster reconstruction study

Run after Gate 0B defines geometry, in parallel with Slices 1-5. Compare current bilinear against a small controlled set: bicubic/Catmull-Rom or Mitchell, Lanczos-family reconstruction, sharp-bilinear/integer-aware scaling where applicable, and one lightweight adaptive sharpening option.

Test Word, Excel and browser text at 2x/3x/4x first, including 100% and 150% Windows scaling, ClearType on/off, and moving/scrolling text for shimmer and temporal instability. Do not introduce semantic text rendering in this track.

### B. UI/DPI/hotkey/localisation foundation

Can proceed in files isolated from runtime extraction. Minimum work: AltGr collision test on Romanian Programmers and German layouts; replace fragile text-caption lookup with control IDs where present; prepare string resources before settings UI grows; make Settings/Help layouts DPI/text-scale aware; keep persistence/diagnostic identifiers language-neutral.

### C. Windows Magnifier + early user/assessor evidence

Add Windows Magnifier as the free baseline comparator. Run small formative sessions as soon as practical: Context + Detail versus full-screen magnification, orientation/recovery tasks, typical Word/Excel/browser work, and perceived text quality at actual working zoom. This should influence product defaults and later P1/P2 features, not block Slices 1-5.


### D. Same-monitor capability spike

Before promising full-screen self-magnification or a one-monitor lens/contextual mode, test recursion exclusion; click, drag, selection and wheel correspondence; cursor duplication/hiding; focus retention; Start / Alt+Tab / notifications / menus z-order; elevated-window boundary; and WGC versus Windows Magnification API where useful.

Outcome may be support through the normal WGC presenter, a different backend, a bounded/windowed mode, or deferral.

### E. Compatibility ledger

Grow current smoke evidence into task-level compatibility over time. Release-critical families should eventually include Windows shell/dialogs, Word, Excel, Outlook, Edge/Chrome, Teams/WebView/Electron, PDF, and the pilot user's essential application. Track application version, Windows build, DPI/topology, evidence-provider health, movement correctness, overlay correctness and recovery.

## 19. Slice-level preservation protocol

Because the repository already contains substantial dirty/uncommitted work:

Before each implementation slice:

1. record branch/HEAD;
2. inventory relevant touched tracked/untracked files;
3. classify pre-existing work versus slice work;
4. avoid reset/clean/checkout of unrelated files;
5. keep the slice file set as small as practical.

After each slice:

1. run its unit/replay tests;
2. run canonical two-screen acceptance;
3. record telemetry/evidence path;
4. inspect diff for unrelated changes;
5. update STATUS only after evidence passes;
6. stop rather than layering the next slice onto a failing one.


## 20. What is deliberately not in the first implementation sequence

Do not fold these into Slices 1-5:

- 3/4-monitor UI;
- same-monitor full-screen magnification;
- Tethered-style semantic relocation;
- app-specific profiles;
- semantic text re-rendering;
- clean-text view;
- clone/presentation modes;
- Span;
- OCR/Reader/camera/touch;
- broad dealer/pricing work.

Architecture seams should emerge from generic source/view/state contracts, not speculative feature classes.
