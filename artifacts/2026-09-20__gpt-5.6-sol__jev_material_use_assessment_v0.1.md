# Jev — material-use assessment for Visual development v0.1

**Date:** 2026-09-20  
**Project:** Visual  
**Scope:** whether Jev from TypeSafe AI can materially accelerate Visual development/orchestration, rather than being adopted because it is new.

## Executive conclusion

Jev is **not a replacement coder for GPT/Codex, Muse or Gemini**. It is a fast typed decision model: structured state goes in and typed Choice / Score / Boolean-style judgments with probabilities come out. It does not generate arbitrary code or prose.

For Visual, Jev is potentially useful only where development currently pays repeated multi-second LLM latency for small decisions that can be expressed as bounded choices. The most promising candidates are:

1. delegated-agent routing;
2. build/test/log triage;
3. continue / retry / stop / escalate gates in automated experiments;
4. cheap pre-screening before an expensive review model.

It is **not currently justified** in the Visual runtime magnification path, POI tracking, viewport control, deterministic test mechanics, or as a general coding agent.

Recommendation: **do not integrate Jev into the production bridge yet.** First collect real routing/triage decisions from Visual development and benchmark Jev against deterministic rules plus the existing models. Integrate only if it measurably reduces wall-clock time/cost without materially worsening routing accuracy.

## What Jev actually is

TypeSafe AI introduced Jev on 2026-09-15 as a "System One" model aimed at fast structured decisions rather than autoregressive text generation.

Official sources:

- TypeSafe launch: https://typesafe.ai/blog/introducing-system-one-models-and-jev
- Official JS/TS SDK: https://github.com/typesafe-ai/typesafe-sdk-js
- Vercel AI Gateway integration: https://vercel.com/changelog/typesafe-ai-jev-now-available-on-ai-gateway
- Vercel model page: https://vercel.com/ai-gateway/models/jev

The official JavaScript/TypeScript SDK is `@typesafe-ai/sdk`, requires Node.js 20+, and is MIT licensed.

## Performance/cost claims — useful but not yet independent proof

TypeSafe currently advertises roughly:

- 70–500 ms end-to-end response time;
- ~$0.042 per million input tokens direct from TypeSafe;
- no metered output-token cost;
- up to 193.6x faster and 444.6x cheaper than LLMs in its own workflow evaluations.

TypeSafe explicitly states those 193.6x / 444.6x numbers are at the high end of expected real-world gains and come from workflows produced by members of its own capabilities team. They should therefore be treated as vendor benchmark evidence, not as a Visual planning assumption.

Vercel currently lists Jev at approximately $0.04/M input tokens through AI Gateway.

## Material opportunities in Visual

### 1. Agent routing — strongest candidate

Current Visual delegation can use GPT/Codex, Muse and Gemini. Choosing an agent is often a bounded decision rather than a generative task.

Possible Jev input:

- task text;
- files affected;
- estimated task size;
- whether current implementation must be inspected;
- whether visual/UI reasoning is required;
- whether independent review is desired;
- whether code modification is authorized.

Typed output could be:

- `codex`
- `muse`
- `gemini`
- `primary_sol_only`
- `no_agent_needed`

plus probability/confidence.

Material benefit would exist only if this replaces repeated expensive LLM routing calls or allows many small tasks to be delegated automatically. At current Visual task volume, deterministic routing plus primary-model judgment may already be fast enough, so this should be benchmarked rather than assumed.

### 2. Build/test/log triage — plausible candidate

After deterministic parsing extracts structured evidence, Jev could classify a run into a bounded set such as:

- compile error;
- test assertion failure;
- timeout/hang;
- display/session invalid;
- capture failure;
- render/present failure;
- telemetry anomaly;
- environment/toolchain issue;
- needs human/model review.

This can be useful if hundreds of automated runs accumulate. Today the run volume is still low enough that ordinary code/rules are simpler.

Important principle: deterministic parsers should extract facts first. Jev should only decide where rules become brittle.

### 3. Experiment orchestration gates — good future fit

The automated Spike 1 harness already creates structured telemetry and scenario state. A future experiment controller could ask bounded questions such as:

- is the run valid enough to analyze?
- should this configuration be repeated?
- is this anomaly likely environmental or product-related?
- should the next test switch zoom, monitor topology or workload?
- is confidence high enough to proceed without an expensive reviewer?

This is a natural Jev shape because the outputs are decisions, not prose.

### 4. Cheap pre-review gate — possible

Jev could score whether a diff/run/report contains enough risk or novelty to justify a Muse/GPT/Gemini review. This could reduce expensive reviews when development volume becomes high.

For Visual today, review volume is not yet large enough for this to be a priority.

## Where Jev is not materially useful

### Coding

Jev does not generate arbitrary source code. It cannot replace Codex/Muse/Gemini for implementation, debugging or architecture work.

### Visual runtime tracking

Do not put a cloud Jev request in the low-vision interaction loop. Even 70–500 ms is far too slow and unreliable for pointer/caret/focus viewport control, where deterministic local processing and frame-scale timing matter.

### Deterministic measurements

Do not use Jev to decide facts already available from telemetry, ETW, WGC/D3D timings, display topology or test assertions. Rules are faster, cheaper and auditable.

### Doxa installation core

The deterministic installer/diagnostic agent should remain functional without AI. Jev could later cheaply classify diagnostic states or decide which support flow to invoke, but it should not own privileged installation actions.

## Maturity risk

Jev is extremely new: public launch was 2026-09-15.

As of 2026-09-20, the official TypeScript SDK repository still has open issues including:

- request shapes that the API can reject;
- numeric choice typing problems;
- a cancellation/native-fetch issue reported to terminate Node 20/22 processes.

Source: https://github.com/typesafe-ai/typesafe-sdk-js/issues

That is enough reason not to add it to `bridge/server.mjs` yet. The bridge is critical development infrastructure and should not absorb a five-day-old SDK without a demonstrated gain.

## Proposed evidence-based spike

Do not start this until we have at least ~30–50 real Visual decisions worth routing/triaging.

Create a small offline corpus from existing work:

- task/routing decisions;
- build/test failures;
- telemetry anomalies;
- review/escalation decisions.

For each item, record the decision eventually accepted by the primary developer.

Compare:

1. simple deterministic rules;
2. Jev;
3. one fast existing model (e.g. GPT Luna or Gemini Flash);
4. primary GPT-5.6 Sol judgment as reference where needed.

Measure:

- agreement with accepted decision;
- high-confidence error rate;
- wall-clock latency;
- cost;
- percentage safely handled without a slower model;
- engineering complexity added to the bridge.

Adoption criterion should be material, for example:

- clearly lower routing/triage latency across real development volume;
- no unacceptable high-confidence misroutes;
- meaningful reduction in expensive model calls;
- integration remains optional and failure-safe.

If it only saves fractions of a second on a handful of decisions per day, do not integrate it.

## Current decision

**Watch and benchmark later; do not integrate now.**

Jev is technically interesting and unusually well matched to agent routing/triage, but Visual does not yet have enough repeated decision volume for it to be a material development accelerator. The correct next step is to accumulate real decision data, not add another AI dependency.
