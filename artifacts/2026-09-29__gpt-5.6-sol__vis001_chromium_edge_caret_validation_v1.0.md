# VIS-001 Chromium / Edge editing-caret validation v1.0

**Date:** 2026-09-29
**Host:** MARIUS-DELL
**Repository:** C:\dev\Vision
**Work item:** VIS-001 - Close/bound Chromium/Edge editing-caret support

## Conclusion

VIS-001 is closed at a deliberately bounded compatibility level.

Vision's existing UI Automation provider is sufficient for the deterministic Microsoft Edge HTML textarea scenario when the editable element actually owns UIA keyboard focus. No product-provider code change was required.

The validated claim is not "all Chromium editors work". It is:

- Microsoft Edge ProductVersion 153.0.4234.48;
- deterministic local HTML textarea fixture;
- textarea exposed as UIA ControlType.Edit;
- AutomationId=e;
- FrameworkId=Chrome;
- TextPattern exposed;
- keyboard caret movement performed during the measured phase;
- Vision 2x tracking/render path active on the current two-display MARIUS-DELL setup.

Custom contenteditable implementations, rich-text editors, embedded Chromium frameworks and other browser/version combinations remain outside this validation boundary until separately exercised.

## Why earlier results were inconsistent

Historical browser-smoke runs alternated between strong semantic-caret evidence and focus/pointer-only results.

Investigation on 2026-09-29 found two harness defects:

1. after starting Vision, the smoke brought the Edge window to the foreground but did not deterministically reacquire the textarea's UIA keyboard focus;
2. the smoke posted WM_CLOSE but did not ensure Vision exited through its real product shutdown path, so a dev Vision instance could survive into the next run and contaminate single-instance and telemetry behaviour.

The old pass rule also accepted any run with more than zero semantic-caret frames. That was too weak to support a compatibility claim.

A direct UIA probe confirmed that Edge exposes the fixture textarea as an Edit element with AutomationId=e, FrameworkId=Chrome, keyboard focus capability and TextPattern.

## Harness correction

app\run-browser-editing-smoke.ps1 now:

- refuses to run over an existing dev visual_app.exe instance;
- locates the fixture editor by UIA AutomationId=e;
- verifies it is keyboard-focusable and exposes TextPattern;
- explicitly sets UIA focus before Vision starts and again after Vision starts;
- scopes all evidence to the keyboard-editing phase;
- requires at least 70% UIA caret presence and 60% caret selection;
- reports fresh pointer interference separately;
- exits Vision through Ctrl+Alt+Q first so telemetry closes normally;
- kills only its own Edge profile processes and force-stops Vision only as a final fallback.

## Product-code decision

No change was made to app\src\tracking\uia_evidence_provider.h.

The evidence did not justify adding hierarchy traversal, browser-specific logic or a Chromium special case to production code. Doing so would have treated a test-focus defect as a product defect and increased maintenance risk without demonstrated user value.

## Acceptance boundary

For the current alpha, the following is acceptable:

- ordinary Edge textarea caret tracking is supported by deterministic regression evidence;
- the support claim stays limited to the tested scenario;
- a materially different editor is a new compatibility case, not evidence that this validation was false;
- future reports should capture Vision version, browser version and editor type before changing the provider.

This satisfies VIS-001's done condition: a supported scenario passes a deterministic test repeatedly, and the untested boundary is explicit.
