# Interaction cadence fix and browser compatibility v0.1

**Date:** 2026-09-23
**Project:** Visual
**Status:** fast-pointer/caret-lag architecture corrected and automatically validated; Chromium editing caret still needs reliable validation

## Human defect that triggered this work

During the first real two-screen task-use session, ordinary caret navigation at 2x felt very responsive. Repeated fast mouse movement exposed a different behavior:

- Detail could feel roughly two seconds behind during faster mouse movement;
- the pointer cross could remain visible for about one second before returning to a caret locator.

The pre-fix telemetry did not show Present failures, but did show occasional long capture/render gaps and outlier pointer-to-caret handoffs.

## Root cause identified

The production app sampled POI evidence, ran the viewport policy and rendered Detail only from the Windows Graphics Capture `FrameArrived` callback.

Cursor capture is intentionally disabled. Therefore hardware-pointer movement over otherwise static desktop pixels is not a reliable reason for WGC to provide a fresh source frame. User-interaction cadence was incorrectly coupled to source-pixel cadence.

This architectural coupling could make pointer/locator/viewport updates late even when the GPU renderer itself was healthy.

## Correction

`app/src/main.cpp` now separates two loops:

1. **WGC callback**
   - acquires current source frames;
   - copies the latest source texture into a renderer-owned cached texture;
   - handles capture content-size changes;
   - does not own tracking cadence.

2. **Interaction/render loop (~60 Hz)**
   - samples Win32 pointer/caret/focus evidence;
   - snapshots UIA evidence;
   - arbitrates current POI;
   - updates viewport/controller state;
   - renders the cached latest source texture;
   - emits telemetry.

D3D11 immediate-context access is serialized so WGC cache updates and render/present cannot race.

## Provider resilience / instrumentation

`Win32EvidenceProvider` now exposes the real last-pointer-movement QPC timestamp.

`UiaEvidenceProvider` now exposes diagnostic snapshot state:

- UIA sample timestamp;
- current semantic-caret availability;
- current UIA-focus availability.

A single transient UIA semantic-caret miss no longer immediately destroys the last valid caret candidate. The last real caret may remain in the candidate set **with its original timestamp**; the existing 250 ms freshness policy therefore expires it naturally. The provider never retimestamps a cached caret and does not fabricate a new position.

Telemetry preserves the original CSV fields and appends:

- `pointer_age_ms`;
- `uia_snapshot_age_ms`;
- `uia_caret_present`;
- `uia_focus_present`;
- `selected_poi_age_ms`;
- selected POI screen rectangle.

These fields make future pointer/caret handoff failures directly diagnosable.

## Browser / Chromium compatibility

A deterministic Edge editing fixture was added:

`app/run-browser-editing-smoke.ps1`

Edge itself rendered with zero Present failures, but the automated editing phase repeatedly ended up with Visual selecting the browser/window focus rectangle rather than a text caret.

Important nuance: telemetry from the Edge run **did show valid UIA TextPattern caret evidence during initial frames**, including a caret-sized selected rectangle. The semantic caret then disappeared and focus-only evidence remained during the measured phase.

Chromium documentation confirms that renderer accessibility can be forced with `--force-renderer-accessibility`, and that Chromium's native UIA provider can be enabled with `--enable-features=UiaProvider`. The harness exercised both, but still did not keep a semantic caret reliably available during the deterministic phase.

Current conclusion:

- do not claim browser caret support is validated;
- do not claim Visual's UIA algorithm is fundamentally incompatible with Edge, because valid Edge TextPattern evidence was observed transiently;
- browser content/keyboard-focus behavior and Chromium's accessibility-provider behavior require a dedicated follow-up;
- this is now an explicit compatibility item rather than a blocker for the corrected render-cadence architecture.

## Interpretation

The specific fast-mouse / delayed cross-to-caret defect found by the first human task-use session has strong automated evidence of architectural correction.

A short human regression is still required when the user is back at the machine, because perceived motion quality cannot be established from telemetry alone.

The highest-value next work is:

1. human regression of fast pointer + caret handoff;
2. Context/Reference experiment preparation and testing;
3. targeted Chromium accessibility investigation, bounded so it does not expand Visual into a general browser-accessibility project.
