## Geometry defect discovered

The provider reports the empty search insertion selection as degenerate, but both:
- GetBoundingRectangles on the degenerate selection, and
- ExpandToEnclosingUnit(TextUnit_Character)

return the entire focused search control rectangle rather than a caret-sized or character-sized rectangle.

Measured geometry:
- focused control: 1510,195 to 1814,242 = 304 x 47 px;
- degenerate selection: same 304 x 47 px;
- character expansion: same 304 x 47 px.

Canonical geometry run:
lab/benchmarks/teams_shell_probe/2026-10-02_01-22-34__range_geometry

Therefore this provider state contains text semantics but no reliable caret position.

This was a false semantic-caret classification, not a rendering failure.

## General fix

Vision now rejects a degenerate semantic-caret rectangle when it is essentially control-sized in both width and height.

The rule is implemented in the pure POI core and used by the UIA provider for:
- TextPattern2 caret ranges;
- ordinary TextPattern degenerate selections.

If direct range geometry is implausible, the provider also tries character-context expansion. If that is still control-sized, no semantic caret candidate is emitted and the existing focus candidate remains available.

This is a provider-quality sanity rule, not a Teams-specific branch.

## Compatibility conclusion

For Teams 26225.1806.5074.1452 global search on this host:

- focus accessibility is usable;
- the empty search control does not expose a trustworthy caret position through the tested UIA TextPattern geometry;
- Vision now safely falls back to focus instead of treating the whole control as a caret;
- rendering remained stable in the exercised workload.

Ledger status should therefore be Bounded-good for global-search focus tracking, with caret precision unavailable in this tested provider state.

Do not generalise this result to Teams chat compose or other Teams workflows. Those remain separate compatibility work.
