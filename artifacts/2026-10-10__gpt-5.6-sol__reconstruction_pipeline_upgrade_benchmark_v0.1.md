# Vision reconstruction pipeline upgrade benchmark v0.1

Date: 2026-10-10
Subject: the same isolated Vision Release executable used in the first calibration
SHA-256: 5DFC4EB59B21F333EE59DE84C354B52C08ECF31DCB04F72F9661EAE98BF9C38E

## Question

Do three proposed improvements materially improve the original Vision binary-reconstruction exercise?

1. persistent/cached Ghidra analysis;
2. capa capability discovery;
3. optional Jev metadata triage.

This is a repeat analysis of a known subject, not a new blind test.

## Baseline

Original calibration:
- 7 strong/exact answers;
- 1 partial answer;
- 2 explicit unknowns;
- no material high-confidence false claim;
- simple score: 7.5/10;
- full Ghidra analysis/decompile queries typically about 3-5 minutes;
- targeted decompile observed at roughly 300 seconds.

The two unresolved questions were:
- exact source-display/source-rectangle filtering policy;
- exact 500 ms topology reconciliation delay.

## 1. Persistent Ghidra cache

Implemented:
- hash-keyed saved Ghidra project;
- warm metadata/xref query;
- warm targeted decompile query;
- Java headless extraction script.

Measured:
- one-time cold Ghidra analysis/save: 204.562 s;
- warm metadata/xref query: 18.753-20.786 s;
- warm full targeted decompile: 121.454-122.337 s;
- successful deep result: 70,816 decompiled characters.

Interpretation:
- repeated structural queries are about 10x faster than the cold analysis;
- repeated deep decompilation is about 2.5x faster than the previous roughly 300 s path;
- the same target function and topology/windowing evidence were recovered.

Accuracy:
- no new trustworthy answer to the two unresolved calibration questions;
- a first detector appeared to find literal 500, but inspection showed this was a false match on function addresses ending in 500;
- the harness was corrected to require an actual standalone numeric literal.

Decision:
**Keep. Make persistent Ghidra projects the default for repeated work on one binary/version.**

## 2. capa

Installed:
- flare-capa 9.4.0 in isolated Python environment;
- official capa 9.4.0 rules;
- official capa FLIRT signatures.

Stock scan:
- 133.102 s;
- 31 capability matches;
- mostly generic Windows behavior: file/registry/process/thread/window/WinHTTP/mutex and similar capabilities;
- did not resolve either missing Vision question.

A four-rule domain pack was then tested using only evidence already visible in the original source-hidden calibration:
- WGC + D3D11;
- pointer + GUI focus evidence;
- workspace topology generation telemetry;
- output-window capture exclusion.

Domain scan:
- 104.952 s;
- 4/4 intended capabilities matched correctly.

Interpretation:
- capa converts low-level clues into a useful semantic index;
- on this small Vision binary it is much slower than simple imports/strings/runtime module probes;
- it added organisation, but not a new correct answer to the ten calibration questions.

Decision:
**Keep as an optional discovery/indexing tool, not in the default critical path.**
Use it when a future binary is large/unknown enough that capability indexing can reduce search space.

## 3. Jev triage

Implemented:
- a small metadata-only adapter;
- bounded candidate list;
- Choice + Score style structured questions;
- dry-run by default;
- refuses a live request without JEV_API_KEY;
- no binary or decompiled code is included in the payload.

Dry-run:
- 6 candidates;
- 12 structured questions;
- local payload preparation: 0.211 s;
- payload file: about 8 KB;
- no network transmission.

A live benchmark could not be run:
- no Jev/TypeSafe API credential is configured on Dell;
- no Jev/TypeSafe ChatGPT plugin is available.

Therefore there is no measured Jev latency or accuracy result.

Decision:
**Do not put Jev in the default pipeline yet.**
The adapter is ready for a later measured test if a credential is supplied and a real candidate-ranking bottleneck appears.

## Accuracy comparison

Baseline: 7.5/10.
Upgraded pipeline: still 7.5/10 on this test.

This is a positive result, not a failure:
- speed improved materially;
- semantic organisation improved;
- no additional unsupported claims were introduced;
- the two genuinely difficult policy questions remained unresolved instead of being guessed.

## Recommended default pipeline after this benchmark

1. Fast deterministic first pass:
   - PE imports;
   - strings/RTTI;
   - ListDLLs/process/window/runtime probes;
   - controlled black-box behavior.

2. Persistent Ghidra project per binary hash:
   - analyze once;
   - reuse for xrefs and targeted decompilation;
   - use lightweight metadata queries before deep decompile.

3. capa only when discovery/search-space reduction is useful.

4. Jev only after a live benchmark proves it improves candidate ranking enough to justify the extra model hop.

5. ETW/ProcMon/debugger/Frida remain escalation tools for unresolved runtime policy.

## Bottom line

The main improvement is speed, not reconstruction accuracy.

Persistent Ghidra caching is clearly worth adopting.
capa is useful but optional.
Jev remains an unmeasured experiment.

The upgraded lab should therefore be simpler than originally proposed: fast Windows evidence + cached Ghidra by default, with capa/Jev added only when the problem warrants them.
## ZoomText 2026 pilot: managed-first reconstruction

A narrow pilot was then run against the installed ZoomText 2026 build, scoped only to Word caret tracking.

### Static result

The managed assemblies were highly recoverable with ILSpy and exposed the caret path directly:

1. UI Automation subscribes to TextPattern.TextSelectionChangedEvent.
2. The event is normalized to ZoomText's internal EventTypeTextSelectionChanged.
3. UiaEventForward creates a text item and retrieves GetTextCursor().
4. A caret change becomes AhoiEventType.ActiveChanged.
5. The event carries an explicit trackingEnabled flag and caret/text object data.
6. AhoiEvernixBase forwards that event into the native callback boundary.

The same install also exposes fallback/provider paths for MSAA caret and a separate screen-model-backed AHOI provider with caret rectangles, text positions, GetCaretRect, and ScrollIntoView.

ZoomText's public COM interfaces expose a distinct magnification tracking subsystem:
- ITracking.Enabled;
- ITracking.TrackTo(IRectangle);
- ITracking2.TextCursorEnabled;
- ITracking2.MousePointerEnabled;
- separate control/window/menu/tool-tip tracking switches.

This gives high confidence that ZoomText separates:
- evidence/provider acquisition;
- AHOI normalization;
- tracking policy/state;
- magnified viewport movement.

### Native Ghidra result

A cold Ghidra analysis was attempted on the 32 MB native Zt.exe.

Measured:
- wall time: 1,340.624 s;
- analysis timeout: 1,200 s;
- import/post-script returned exit 0;
- project save failed;
- the requested TextCursorEnabled literal produced no Ghidra-defined string/xref hits;
- a separate PE/Capstone scan found the literal strings but no direct RIP-relative xrefs.

This is materially worse than the Vision binary path and is not a useful default for this target.

Decision:
**Do not make whole-EXE Ghidra analysis the first native step for large mixed managed/native accessibility products.**

For this class of target, use:
1. managed assembly/type discovery first;
2. public COM/interface reconstruction;
3. controlled runtime evidence;
4. only then targeted native analysis around a concrete callback/function boundary.

### Live-test boundary

The installed ZoomText build requires a Windows restart to enter its 40-minute demo mode.

No unattended reboot was performed.

Before the live phase:
- the ZoomText runtime was returned to its pre-pilot stopped state;
- current user settings/registry were backed up;
- a 32-bit COM live harness was prepared and syntax-validated;
- the harness uses a disposable synthetic Word document only;
- it samples ZoomText PrimaryWindow.View plus UIA caret geometry;
- it temporarily sets 4x zoom + text-cursor tracking with pointer tracking disabled;
- it restores the prior ZoomText zoom/tracking state and closes Word without saving.

The live run is still required to prove that Word caret movement exercises the reconstructed tracking path and moves the viewport accordingly.

### Pipeline refinement from the ZoomText pilot

The earlier default pipeline should therefore be refined:

1. Fast deterministic first pass.
2. **Managed-first branch when .NET/mixed-mode assemblies are present.**
3. Public COM/type-library/interface reconstruction where available.
4. Controlled runtime correlation.
5. Cached Ghidra only after a concrete native boundary has been identified.
6. capa/Jev/ETW/debugger only when they reduce a specific unresolved search space.

This pilot improved the pipeline design even before the rebooted runtime phase: it avoided spending further time on a native monolith after the managed architecture had already exposed the useful caret-tracking boundary.
