# Vision pre-Opus product and development plan v0.1

**Date:** 2026-09-29  
**Status:** Proposed plan for independent architectural/strategic review; not yet approved for implementation  
**Inputs:** live Vision codebase, incumbent feature/commercial research, existing regression evidence, and Dell competitor-research bench.

## 1. Product definition to test

Vision should be one Windows application for low-vision users with useful functional vision. It should work on ordinary Windows systems with **2, 3 or 4 monitors**, irrespective of Doxa hardware. Doxa should later be a well-qualified hardware configuration, not a separate Vision codebase.

Initial product intent: deliver a smaller, clearer subset of high-value visual-access functionality rather than reproduce ZoomText/SuperNova breadth. Full screen-reader and Braille functionality are outside the initial product boundary.

English is the first shipping language, but the software should become localisation-ready before the UI grows further.

## 2. What is already built and should be preserved

- Windows Graphics Capture of a physical source monitor.
- D3D11 crop/scale/render pipeline with a steady ~60 Hz interaction/render loop.
- independent pointer, Win32 caret/focus and UI Automation caret/focus evidence.
- freshness/intent arbitration and a viewport controller with comfort margins.
- Context screen View Locator plus full-screen Detail output.
- independent pointer/caret/focus locator controls.
- 1x, 1.5x, 2x, 3x and 4x zoom, including exact temporary-1x return.
- Normal, increased-contrast, inverted and grayscale rendering modes.
- persisted Context/Detail/Reference selections.
- native Settings, Help and Ask Vision.
- Velopack install/update, diagnostics, single-instance behaviour and current two-screen acceptance/regression harnesses.

This foundation is real and should be evolved, not replaced casually.

## 3. Current architectural limitation

The runtime enumerates any number of monitors, but the active product model is still **one source monitor -> one CaptureRunner -> one Renderer/Detail window**, with one optional Reference monitor that Vision leaves untouched. Settings likewise persist exactly three named roles: Context, Detail and Reference.

Therefore 3/4-monitor product support is not achieved by exposing more combo boxes. It requires generalising the source/output/view model while keeping the current two-monitor behaviour as a supported preset.

## 4. Proposed architecture direction for review

The proposed direction is to separate **capture sources** from **view outputs**. This is a design hypothesis for Opus review, not an implementation decision yet.

### 4.1 Monitor registry

Create one monitor/topology service responsible for enumeration, DPI, geometry, topology changes and stable identity. Do not continue to treat `\\.\DISPLAY1`-style device names as the long-term identity because they can change. Prefer DisplayConfig/EDID/path identity with graceful fallback. Doxa-specific controller identity remains outside Vision.

### 4.2 Capture source objects

A `CaptureSource` represents a physical monitor (and potentially later a window) whose pixels are being captured. It owns WGC lifecycle and the latest source texture, but not viewport policy or an output swap chain. Multiple output views should be able to consume the same source without starting duplicate captures.

### 4.3 Shared evidence hub

Pointer and semantic accessibility evidence should be sampled centrally in virtual-desktop coordinates. A shared `EvidenceHub` owns Win32/UIA sampling and timestamps. Each view can then filter candidates to its configured source and apply its own follow policy. This avoids running multiple competing UIA evidence providers merely because several monitors are magnified.

### 4.4 View sessions

A `ViewSession` ties together: a source binding, a destination monitor/window, its own viewport controller, zoom/visual settings, and a render target. This is the unit that should scale from one Detail view to several independent or cloned views.

Examples the model must express:

- current Vision preset: monitor A remains Context at 1x; monitor B displays a magnified view sourced from A;
- independent multi-monitor: monitor A magnifies A, monitor B magnifies B, with different zoom/colour if desired;
- 3/4 monitor hybrid: one Context source, one or two Detail views, plus one normal unmanaged Reference display;
- later clone/presentation mode: two output monitors consume the same source with different visual settings.

### 4.5 Rendering device strategy

The current `Renderer` owns its D3D11 device, WGC interop device, cached source texture, swap chain and shader pipeline. For several outputs there are at least two credible designs:

A. one shared D3D11 device/capture cache plus per-view swap chains and render state;
B. one renderer/device per output with source sharing/copying across compatible devices.

The plan currently favours A for resource efficiency and simpler texture sharing, but this is explicitly a point for Opus to challenge against WGC threading, multi-adapter/hybrid-GPU behaviour and failure isolation.

### 4.6 Same-monitor magnification

Generic multi-monitor Vision must not assume a separate Detail monitor. A monitor may need to display a magnified view of itself while other monitors do the same. The current single-monitor fallback already proves the basic self-capture-exclusion idea. The general architecture should make same-monitor and cross-monitor bindings first-class rather than separate products.

### 4.7 Pointer-boundary policy

Monitor crossing becomes a central multi-monitor interaction rule. The current build drops pointer evidence when the pointer leaves the configured source monitor, allowing semantic focus to take over and sometimes causing a jump. SuperNova Mouse Buffer is strong incumbent evidence that this boundary is a real user problem.

The preferred hypothesis to test is a deliberate boundary policy: hold the current pointer-driven viewport when the pointer leaves its source, suppress incidental fallback, and release that hold either when the pointer returns or when a fresh strong caret/focus action indicates real keyboard intent. Optional edge resistance / explicit monitor switching can be tested later.

### 4.8 Text quality is an architectural gate

ZoomText xFont/smoothing and SuperNova True Fonts/Bold Fonts may be more important than additional zoom modes. Vision currently scales captured raster pixels. Before committing to the final rendering architecture, hands-on comparison at 2x-4x in Office/Edge must establish whether Vision image quality is acceptable or whether a semantic text-enhancement path is needed.

Possible future approaches range from better reconstruction/sharpening in the render pipeline through targeted DirectWrite/UIA overlays to a much deeper semantic re-rendering model. The latter could multiply complexity and should not be chosen without evidence. This is a primary Opus review question.

## 5. Localisation foundation

The current Win32 UI is Unicode-capable, but user-facing English strings are heavily hard-coded. A quick live-code audit found wide-string literals concentrated in `main.cpp`, `settings_window.cpp`, `help_window.cpp`, `help_catalog.h` and `hint_window.cpp`, with no current general UI resource catalogue.

Before adding substantial UI, introduce a stable string-key layer with English (preferably en-GB) as the required fallback. Settings must continue to persist language-neutral enums/IDs, not translated labels. Layout helpers should permit longer strings and later right-to-left review without changing feature logic.

The first release remains English-only. No translation work is required now; only localisation readiness.


## 6. Development sequence proposed for review

### Stage 0 - finish incumbent validation

Use the prepared Dell rig to run the same pointer, caret, focus and monitor-crossing scenarios against ZoomText and SuperNova, plus manual feature walkthroughs for text smoothing, view modes, Freeze/Hooked Areas, configurations and multi-monitor modes. This stage may alter priorities but should not alter Vision code.

### Stage 1 - architecture extraction with zero intended feature change

Refactor the current monolithic runtime into explicit monitor registry, shared evidence service, capture source, view session and render-target responsibilities while preserving the exact validated two-screen Context + Detail behaviour. Every refactor slice must run the existing two-screen acceptance suite.

The purpose is to make later 2-4 monitor work additive rather than a fork or rewrite.

### Stage 2 - localisation-ready UI foundation

Move user-visible strings behind a resource/string catalogue and remove language-dependent values from state. Keep English only. Do this before expanding settings and feature UI.

### Stage 3 - generic 2-4 monitor core

Replace the fixed Context/Detail/Reference persistence model with a versioned workspace/view configuration capable of describing up to four displays. Preserve the current Context + Detail workflow as the default two-monitor preset.

Add same-monitor magnification, multiple concurrent view sessions, per-view zoom/visual settings, stable monitor identity/recovery, topology changes, and an explicit cross-monitor pointer policy.

Automated tests should simulate several display topologies even before physical 3/4-monitor hardware arrives. Physical performance/usability claims remain limited to the Dell two-screen bench until Doxa or another 3/4-monitor setup is available.

### Stage 4 - focused magnifier-core quality

Close the remaining high-value incumbent gaps rather than adding breadth:

- text quality/smoothing decision and implementation;
- richer but simple colour and visual-enhancement presets if validated;
- application compatibility matrix for Word, Excel, Outlook, Edge/Chrome, Teams/Electron and common Windows UI;
- viewport/panning tuning with low-vision users;
- pointer/caret/focus locator refinement;
- zoom-step/fractional preferences only where users need them.

### Stage 5 - selectively add second-layer capabilities

Only after the focused core is stable, test and choose among: simple app-specific profiles, pinned/Hooked-Area-style regions, collaboration/clone, presentation mode, visual reading modes, and basic speech/read-aloud. Each addition requires explicit user value and support-cost justification.

### Stage 6 - commercial productisation boundary

After the technical product is credibly scoped, validate with dealers/assessors: required minimum features, expected support/training, funding/procurement requirements, acceptable omissions, deployment requirements and channel economics. Pricing strategy remains a later decision.


## 7. Difficulty assessment

The current evidence supports two different statements that should not be confused.

First, reproducing the **full visible breadth** of ZoomText/SuperNova would be a large and unnecessary undertaking. Their products include decades of compatibility work, many view geometries, reading/speech, enterprise deployment, remote environments, cameras, profiles, specialised navigation and support infrastructure.

Second, building a credible **focused magnifier-only Vision** is materially more tractable because much of the difficult foundation already exists. Vision already captures, renders, tracks pointer/caret/focus, manages viewport movement, provides orientation/1x recovery, applies visual transformations, persists settings and has installation/update/test infrastructure.

A reasonable pre-hands-on estimate is: Vision currently implements roughly **20-30% of the visible magnifier-feature breadth** of the incumbents, but perhaps **45-60% of the foundational engineering needed for the proposed focused Vision core**. These are planning ranges, not measured completion percentages. The remaining work is disproportionately concentrated in hard areas: multi-view architecture, text quality, compatibility coverage and usability tuning.

Therefore the risk is not that we cannot build another zoom control. The risk is that a deceptively small feature list still carries substantial Windows compatibility and QA obligations.

## 8. What should explicitly wait for Opus review

Do not implement the proposed multi-monitor refactor before independent review of:

- whether capture sources and view sessions are the right abstraction;
- shared versus per-view D3D11 device strategy;
- whether same-monitor self-capture is robust enough as a first-class model;
- how to isolate failure when one of several capture sources/topologies changes;
- whether text-quality requirements imply a different rendering architecture;
- whether the proposed `EvidenceHub` creates unwanted coupling between independent monitor views;
- whether the workspace model is sufficiently general without overengineering clone/span/presentation modes;
- whether localisation should be done before or after the architecture extraction;
- whether our first product boundary is commercially coherent given incumbent support/channel dynamics.

## 9. Definition of success for the next implemented Vision milestone

After architecture review and implementation planning, the first major technical milestone should not be feature parity. It should be:

**The existing two-screen Context + Detail workflow still passes its acceptance suite, while the internal model can configure and run multiple independent/cross-monitor view sessions for up to four displays without Doxa-specific assumptions.**

Only then should additional incumbent features be layered onto the product.
## 10. v0.2 architecture corrections from hands-on incumbent research

The following changes supersede v0.1 where there is a conflict.

### 10.1 Add an explicit Visual Overlay / Enhancement layer

Pointer/caret/focus evidence serves two different consumers:

- POI / viewport policy decides what the magnified view follows;
- Visual Overlay policy decides what target or targets should be visibly emphasised and how.

Do not encode locator styling inside POI arbitration or the viewport controller.

A proposed visual-overlay responsibility should support:
- independent pointer, caret and keyboard-focus enablement;
- a small set of high-visibility presets at first;
- per-target shape, size and visibility policy;
- per-ViewSession/per-monitor scope;
- later custom colour, transparency and timing without changing tracking architecture.

This is now first-product core rather than a late refinement.

### 10.2 Preserve a one-monitor contextual-view seam

The first architecture should not hard-code every incumbent zoom-window geometry. It should nevertheless be able to support one non-full contextual view without another foundational rewrite.

The minimum target for review is:
- Full / self-monitor magnification;
- existing cross-monitor Context + Detail;
- one movable or fixed contextual/lens-style view on a single monitor.

Split-screen variants can be expressed later if the view/window abstraction is sound.

### 10.3 Make text enhancement a gated renderer decision

Do not build a semantic text re-renderer during the first architecture extraction.

Instead preserve a rendering seam for:
1. raster scaling baseline;
2. lightweight shader-based sharpening / reconstruction;
3. optional semantic text enhancement only if Office comparison proves it materially necessary.

The pre-implementation Office experiment should compare supported incumbent font paths with Vision at matched practical zoom. Browser comparison is insufficient because SuperNova falls back to Standard smoothing there.

### 10.4 Preserve simple application-scoped settings

The workspace/state model should use stable application identity and permit later overrides for zoom, visual transformations, overlay presets and view assignment. Do not build a complex profile editor in the architecture tranche, but do not make all settings irrevocably global.

### 10.5 Revised sequence within the core

After the architecture extraction is accepted, the focused-core tranche should be ordered approximately as follows:

1. preserve the passing two-screen baseline while extracting monitor/source/view responsibilities;
2. add generic 2-4 monitor workspace semantics and stable topology identity;
3. add explicit per-view visual-overlay policy using the existing pointer/caret/focus evidence;
4. add localisation-ready UI resources before the settings surface grows;
5. qualify a minimal one-monitor contextual view;
6. run the Office text-quality gate and choose raster/sharpening/semantic direction;
7. expand the real application compatibility matrix;
8. add simple application-scoped overrides only after the underlying settings model is stable.

Hooked Areas / Freeze-style regions, presentation/clone modes, Doc Reader and basic speech remain evidence-gated second-layer capabilities.

### 10.6 What Opus must challenge now

The independent review must explicitly assess:
- whether overlay policy belongs per ViewSession, globally, or in a hybrid model;
- whether multiple simultaneous overlay targets create visual overload or architectural coupling;
- whether a one-monitor contextual view should be first-product table stakes;
- whether font enhancement should remain a renderer seam or force a broader rendering redesign;
- whether application-scoped overrides should be designed into the state schema now or deferred entirely;
- whether the proposed multi-monitor abstraction is simple enough given that incumbents already expose many mode-specific concepts.
