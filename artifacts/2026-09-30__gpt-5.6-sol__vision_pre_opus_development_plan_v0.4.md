# Vision pre-Opus product and development plan v0.4

**Date:** 2026-09-30  
**Status:** reconciled proposal for independent Opus review; not approved for implementation  
**Inputs:** live Vision repo; ZoomText comprehensive assessment v0.2; SuperNova comprehensive assessment v0.1; cross-product synthesis v0.1; existing acceptance/regression evidence.

## 1. Product definition under review

Vision should remain one hardware-agnostic Windows low-vision application for users with useful functional vision, intended to work coherently on ordinary 2, 3 and 4 monitor systems.

Doxa is later a qualified hardware configuration, not a separate Vision fork. Doxa Installer remains a separate hardware/setup workstream.

The product hypothesis is **small surface, deep quality**:

- better predictability and lower configuration burden than incumbent suites;
- strong visual tracking and orientation;
- coherent multi-monitor behaviour;
- enough rendering quality and compatibility for sustained workplace use;
- no attempt at initial screen-reader/Braille breadth.

## 2. Current implementation truth to preserve

The current two-screen alpha already has:

- Windows Graphics Capture of a physical source monitor;
- D3D11 crop/scale/render path;
- independent pointer, Win32 caret/focus and UIA caret/focus evidence;
- POI arbitration and viewport controller with comfort margins;
- Context + Detail;
- View Locator;
- exact temporary 1x/return;
- pointer/caret/focus locator controls;
- 1x, 1.5x, 2x, 3x and 4x zoom;
- normal, contrast, invert and grayscale rendering modes;
- persisted Context/Detail/Reference roles;
- Settings, Help and Ask Vision;
- Velopack install/update;
- diagnostics, single-instance handling and two-screen acceptance/regression harnesses.

This foundation is validated and should be evolved incrementally rather than replaced casually.

## 3. Current architectural constraint

The code enumerates multiple monitors but the runtime product model is still essentially:

**one physical source monitor -> one CaptureRunner -> one Renderer/Detail window**

plus one optional unmanaged Reference display.

Therefore genuine 2–4 monitor support requires more than exposing more monitor selectors. It requires separating source capture, evidence, view ownership, per-view state and output rendering while keeping the current two-screen behaviour as a supported preset.

## 4. Research-driven first-product scope

### 4.1 Core

The combined ZoomText/SuperNova research supports these as first-product capabilities:

1. high-quality magnification with practical fractional zoom;
2. pointer, caret and focus tracking;
3. predictable viewport movement and alignment;
4. exact temporary 1x/return and locator/overview orientation;
5. a small set of strong pointer/caret/focus visual cue presets;
6. colour/contrast plus modest brightness/contrast/tint expansion;
7. coherent 2–4 monitor behaviour with per-view state;
8. explicit cross-monitor ownership/boundary policy;
9. renderer-quality extensibility rather than a hard-coded raster-only dead end;
10. persistence, install/update, diagnostics and bounded compatibility;
11. simple contextual help/discoverability.

### 4.2 Preserve architectural seams; do not promise at launch

- one useful single-monitor lens/docked/contextual geometry;
- pinned remote context;
- Tethered-like dynamic context relocation;
- app-scoped settings;
- clone/standard-view collaboration;
- presentation mode;
- optional clean-text/simplified reading view;
- non-visual boundary cues.

### 4.3 Deliberately defer

- Span;
- full incumbent view-mode parity;
- large custom locator/catalogue editors;
- full Situation Settings/profile complexity;
- Reader/AppReader/Doc Reader/Line View as product pillars;
- full screen-reader/Braille functionality;
- OCR/Finder;
- camera/whiteboard;
- touch;
- Secure Mode/logon parity;
- broad Citrix/RDP/virtual-environment promise.

## 5. Proposed architecture hypotheses for Opus to challenge

These are not implementation decisions.

### 5.1 MonitorRegistry

Own monitor enumeration, geometry, DPI, topology changes and stable identity.

Do not treat DISPLAY1-style device names as durable identity. Prefer DisplayConfig/path/EDID-derived identity with graceful fallback.

### 5.2 CaptureSource

Represent a physical monitor as a reusable WGC pixel source.

A CaptureSource should own capture lifecycle and latest source texture, not viewport policy or destination rendering.

Several outputs should be able to consume one CaptureSource without starting duplicate capture pipelines unnecessarily.

### 5.3 EvidenceHub

Sample pointer and semantic accessibility evidence centrally in virtual-desktop coordinates.

The evidence layer should not assume one destination. It should publish time-stamped pointer/caret/focus evidence that downstream ownership/follow policy can interpret.

### 5.4 ViewSession

Represent one independently configurable visual output:

- source binding;
- destination monitor/window;
- viewport controller;
- zoom/visual state;
- overlay/highlight state;
- render target;
- follow/ownership policy.

This must express both same-monitor and cross-monitor bindings.

### 5.5 View ownership / active-follow policy

The incumbent research makes this a first-class decision, not a detail.

Candidate models:

A. **independent following** — each view independently reacts to relevant evidence;  
B. **single active follow owner** — one view moves while others remain stable;  
C. **hybrid ownership** — ownership depends on user activity, source/destination role or explicit switch.

ZoomText is evidence for B-like semantics; SuperNova provides evidence for more independent per-view behaviour. Opus should not assume either maps directly to Vision.

### 5.6 OverlayPolicy separate from ViewportPolicy

Pointer/caret/focus evidence should feed at least two independent consumers:

- viewport movement;
- visible orientation cues.

A view may need a caret wedge or focus frame without moving, or may move without showing a cue. Overlay state should therefore not be buried inside evidence arbitration.

### 5.7 Monitor boundary state

The current build drops pointer evidence when the pointer leaves the configured source monitor, which can allow semantic focus to move the view unexpectedly.

The final policy should explicitly define:

- pointer leaving source/view;
- hold versus semantic fallback;
- deliberate monitor switching;
- optional edge resistance/dwell/push behaviour;
- ownership hand-off.

Do not let these behaviours emerge accidentally from source filtering.

### 5.8 Rendering / text-quality seam

The current raster WGC path remains the baseline.

The architecture should make it possible to add:

- shader/reconstruction improvement;
- targeted text enhancement;
- clean-text views;
- application-specific fallbacks;

without requiring a wholesale renderer rewrite.

Do not commit to xFont/True Font parity. The Word comparison now shows a meaningful xFont advantage at 2x and greater crispness at 4x, but also visible local glyph-shape distortion at 4x. The working renderer strategy is therefore staged: improve raster/GPU reconstruction first, preserve targeted semantic enhancement and clean-text seams, and require further semantic work only if later quality/compatibility evidence justifies it.

### 5.9 Context-management seam

View Locator, temporary 1x, Freeze/Hooked Areas and Tethered View all address context loss.

The proposed architecture should not require a launch implementation of pinned/tethered views, but it should avoid making lightweight sub-views or context relocation prohibitively expensive later.

## 6. Rendering-device question

The current Renderer owns its D3D11 device, WGC interop device, source texture, swap chain and shader pipeline.

Two plausible multi-view designs remain:

A. one shared D3D11 device/capture cache with per-view swap chains and render state;  
B. isolated renderer/device per output with explicit resource sharing/copying.

The current hypothesis favours A for efficiency and texture reuse, but Opus must challenge this for:

- hybrid/multi-adapter systems;
- WGC threading/interoperability;
- device-loss isolation;
- failure containment;
- output refresh-rate differences;
- complexity of same-monitor self-capture.

## 7. Configuration model

Replace fixed Context/Detail/Reference persistence with a versioned workspace model capable of expressing up to four monitors.

Minimum semantics should include:

- stable monitor identity;
- source/destination binding;
- normal/unmanaged versus Vision-managed display;
- zoom/visual state per view;
- follow/ownership policy;
- optional linked settings;
- topology recovery behaviour.

Do not encode every incumbent clone/span/presentation feature into version one.

Application-scoped overrides should be possible later without making the initial settings UI profile-heavy.

## 8. Localisation foundation

English remains the first language.

Before UI breadth expands substantially:

- move user-visible strings behind stable keys;
- keep language-neutral settings values;
- preserve English fallback;
- allow longer translated strings and later RTL review.

Do not turn localisation readiness into a large parallel feature project.

## 9. Proposed development sequence after Opus

### Stage 0 — independent Opus review

Research synthesis is complete enough for review. Opus should arbitrate product scope, view ownership, renderer seams, workspace model and the smallest pre-implementation experiments.

No architecture refactor begins before this review is reconciled.

### Stage 1 — architecture extraction with zero intended feature change

Extract monitor registry, capture source, shared evidence, view/output and overlay responsibilities while preserving the validated current Context + Detail behaviour.

Run existing acceptance tests after each slice.

### Stage 2 — localisation-ready resource layer

Move visible UI strings behind a simple resource catalogue before feature UI expands.

### Stage 3 — generic 2–4 monitor core

Introduce:

- versioned workspace/view schema;
- multiple concurrent view sessions;
- same-monitor and cross-monitor bindings;
- per-view zoom/visual state;
- explicit view ownership;
- explicit monitor-boundary policy;
- topology recovery.

Automate several simulated topologies even before physical 3/4-monitor hardware is available.

### Stage 4 — first-product orientation/visual layer

Add/refine:

- small pointer/caret/focus cue preset set;
- per-view cue policy;
- colour/brightness/contrast/tint controls;
- overview/boundary cues.

Do not build incumbent-scale editors.

### Stage 5 — compatibility and text-quality qualification

Expand application matrix across Office, Edge/Chrome/Firefox, Teams/Electron, WPF/WinUI/Win32 and terminals.

Qualify raster/GPU text quality across common working magnifications and the workplace application matrix. The architecture review no longer needs to decide whether to build a universal semantic renderer; targeted semantic text work should be promoted only if improved raster reconstruction still fails the 2x-3x quality target or specific applications require it.

### Stage 6 — user/dealer validation of next-layer features

Test the value of:

- pinned context;
- Tethered-like context relocation;
- app-specific settings;
- one contextual/lens geometry;
- collaboration/presentation;
- simplified reading view.

Promote only what produces clear task value.

## 10. Main decisions Opus must resolve

1. Is the product boundary coherent?
2. Which candidate first-product features materially affect architecture now?
3. Is MonitorRegistry + CaptureSource + EvidenceHub + ViewSession the right decomposition?
4. What view-ownership model should guide the core?
5. Where should overlay/highlight policy live?
6. What is the minimum boundary-crossing state machine?
7. Should context sub-views be modelled now or safely deferred?
8. Is the proposed staged renderer seam sufficient: improved raster/GPU reconstruction first, targeted semantic enhancement only where justified, and optional clean-text fallback?
9. What workspace schema is minimally future-proof without feature over-design?
10. Which parts of the proposed sequence should be changed before implementation?

## 11. Evidence boundary

Do not imply that every incumbent capability has been behaviourally validated.

Remaining bounded uncertainties include:

- matched 2x Vision-vs-ZoomText perceived quality remains useful as a later release-quality benchmark; 4x comparison already establishes the current crispness-versus-glyph-shape trade-off;
- ZoomText MultiView hand-off feel;
- ZoomText Tethered/Live Text task feel;
- SuperNova Mouse Buffer feel and Hooked-Area task value;
- physical 3/4-monitor usability;
- low-vision user preference among Context+Detail, full-screen and contextual/lens modes.

These are evidence gaps, not automatic blockers. Opus should identify which genuinely need resolution before Stage 1 and which can safely remain staged validation.
