# SuperNova Magnifier comprehensive assessment v0.1

**Date:** 2026-09-30
**Status:** SuperNova feature assessment for Vision pre-Opus product/architecture review
**Product tested:** SuperNova Magnifier 25.05 on MARIUS-DELL

## Purpose

This assessment closes the gap left by the first incumbent benchmark, which over-weighted pointer/caret/focus tracking and under-covered the wider magnifier product surface.

The objective is not feature parity. It is to determine which SuperNova capabilities solve important low-vision problems, which capabilities could materially affect Vision architecture, and which should be deferred or excluded from the first Vision product.

## Evidence model

Conclusions distinguish:
- **Hands-on verified** — directly exercised or visibly observed on the installed 25.05 build.
- **Installed-product verified** — present in the live 25.05 control panel/menu but behaviour not fully exercised.
- **Current vendor documented** — supported by current Dolphin feature/training material.
- **Historical manual detail** — older Dolphin manuals used only where current material is less explicit.

The assessment does not treat a menu item as proof of user value and does not claim hands-on verification where SuperNova's custom rendering/capture layer prevented reliable observation.

## High-level conclusion

SuperNova is not merely a magnifier plus tracking. Its mature product model has five layers:

1. **Magnification and rendering quality** — zoom range, True Font/image smoothing, multiple view geometries.
2. **Following and orientation** — pointer/caret/focus tracking, visual highlights, pointer schemes, Overview Mode and edge/orientation cues.
3. **Multi-monitor workspace control** — independent zoom/colour, Side-by-Side, monitor switching, Mouse Buffer, clone/span/presentation modes.
4. **Context and reading aids** — Hooked Areas, Line View, Doc Reader, save/restore/panning/navigation.
5. **Configuration/adoption/support** — Application Settings, Situation Settings, contextual help, Hotkey Helper, import/export and update/support tooling.

For Vision, the lesson is not to copy this breadth. It is to keep a small surface while treating orientation, multi-monitor behaviour, rendering quality and application compatibility as first-class concerns.

## What hands-on work changed

### Alternative views are product models, not checkbox clutter

Existing live captures in lab/incumbent-research/review/supernova_views show all eight geometries. Split modes, Fixed Window, Magnifying Glass and Resizing Glass preserve context in materially different ways.

The Vision implication is not “implement eight modes”. It is to avoid hard-coding full-screen Detail as the only possible output geometry.

### Orientation is a first-class layer

The live Large Red / Large Yellow preset work and installed highlighting surface confirm that SuperNova treats pointer/caret/focus visibility independently from tracking.

This supports a key Vision architecture correction: **POI/viewport movement and visual overlay/highlighting are separate consumers of the same evidence.**

### Colour is broader than invert/high-contrast

Live captures under lab/incumbent-research/review/supernova_colors show materially different transforms, including colour-deficiency, tint and high-contrast styles.

Vision need not ship 24 presets, but a few strong presets plus brightness/contrast/tint is more defensible than the present minimal set.

### Multi-monitor is a product model, not an output count

SuperNova Side-by-Side combines independent applications, independent magnification, independent colour, separate tracking, explicit monitor switching and Mouse Buffer.

That is stronger evidence for Vision's proposed CaptureSource plus per-ViewSession model than simply knowing SuperNova supports multiple screens.

The important lesson is **per-view independence plus deliberate cross-monitor ownership**, not SuperNova's exact UI.

### Context aids solve attention-distance

Overview Mode, split/lens views, Margin Release and Hooked Areas all solve variants of the same underlying problem: magnification hides context and makes orientation expensive.

For Vision, this design space is more useful than copying feature names:
- recover whole-screen position;
- keep a remote reference visible;
- signal physical/virtual boundaries;
- bring magnification to the point of attention;
- reduce long pans and repeated zoom changes.

## Architecture implications for Vision

### Per-view state is required

A generic 2-4 monitor model must allow at least zoom, visual transform, overlay preset, source/destination binding and viewport policy per view. Global settings alone cannot reproduce Side-by-Side value.

### Monitor boundary policy needs its own design

Mouse Buffer proves that crossing monitors is not a trivial pointer detail. Vision should explicitly model pointer leaving a source/view, viewport hold versus semantic fallback, deliberate monitor switching, and optional edge resistance/dwell/push policy.

This should not emerge accidentally from POI filtering.

### Overlay policy should be independent of viewport policy

Pointer/caret/focus evidence should be reusable for viewport movement, visible cue rendering, cue style/persistence and trainer/sighted-colleague visibility.

### Text quality remains the renderer gate

Dolphin positions True Font as central magnifier quality. We still lack a controlled matched Office comparison against Vision raster scaling.

Do not assume semantic text re-rendering is necessary, but do not close the renderer architecture before a matched 2x/3x/4x Office test.

### App-specific state should be possible, not mandatory at launch

Application and Situation Settings demonstrate value but also complexity. Vision should support later app-scoped overrides without requiring an incumbent-style profile editor in version one.

## Scope to take into Opus

### First-product core

- high-quality magnification;
- pointer/caret/focus tracking;
- predictable viewport movement;
- overview/locator/temporary-normal orientation recovery;
- a small set of high-visibility pointer/caret/focus presets;
- practical colour/contrast/tint controls;
- coherent 2-4 monitor per-view behaviour;
- monitor-boundary policy and explicit monitor switching;
- reliable application compatibility;
- persistence, install/update/diagnostics;
- strong contextual help/discoverability.

### Preserve seams, but do not require for launch

- one useful single-monitor contextual/lens/fixed geometry;
- Hooked Areas / pinned context;
- app-specific settings;
- clone/standard-view collaboration;
- Presentation Mode;
- one basic reading-oriented mode if later justified.

### Defer until user/dealer evidence

- Span;
- full custom highlight editors;
- extensive colour/pointer catalogues;
- Situation Settings complexity;
- Line View / Doc Reader as product pillars;
- touch;
- camera/whiteboard;
- media ecosystem;
- screen-reader/Braille functionality.

## Remaining bounded SuperNova gaps

1. **Matched Office text quality:** SuperNova True Font versus Vision raster scaling at matched 2x/3x/4x.
2. **Mouse Buffer feel:** semantics are clear, but resistance/dwell behaviour has not been cleanly quantified hands-on.
3. **Per-monitor switching:** capability is documented; a clean repeatable two-monitor configuration run would strengthen behaviour evidence.
4. **Custom highlight geometry:** presets and semantics are clear; exact per-cue shape catalogue was not reliably captured.
5. **Line View / Doc Reader value:** mechanics are clear; early-product value needs user evidence, not more black-box automation.
6. **Hooked Area task value:** mechanics are clear; Word/Excel benefit should be user-tested.

Only item 1 plausibly changes the renderer architecture before implementation. Items 2-6 can be carried into Opus as bounded uncertainties or later user-validation gates.

## Bottom line

The broad SuperNova review materially changes the framing, but not toward feature parity.

The strongest lessons for Vision are:
1. **orientation aids belong in the core**, not as cosmetic polish;
2. **multi-monitor means independent per-view state plus deliberate crossing policy**, not merely more outputs;
3. **context loss is a family of problems** addressed by Overview, split/lens views, Margin Release and Hooked Areas;
4. **rendering/text quality is important enough to gate the final renderer decision**;
5. **application-specific automation and reading tools are valuable but complex enough to stay second-layer unless user evidence promotes them**;
6. **help, discoverability and supportability are part of the product**, especially in assistive technology.

This is sufficient to take SuperNova into the independent Opus product/architecture review, provided the Office text-quality uncertainty is explicit rather than silently assumed away.
