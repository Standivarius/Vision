# Vision Opus 5.5 xhigh + GPT-6 Astra xhigh reconciliation v0.1

**Date:** 2026-09-30  
**Status:** independent-review reconciliation; no implementation authorised by this artifact

## 1. Strong agreement

Both reviewers independently support the following direction:

1. Proceed with a narrow, behaviour-preserving architecture extraction. Broad 3/4-monitor qualification, final renderer quality and user preference do not need to block the first structural slices.
2. Keep Context + Detail as the initial/default two-monitor hypothesis, not an architectural invariant. Its user advantage remains unproven.
3. Keep Source / Evidence / View / Destination separation, but add a workspace-level coordinator. Shared evidence must not itself decide which view moves.
4. Use one explicit movement owner initially. Transfer may follow credible user activity, with explicit manual override/switch. Inactive views retain state and may remain live.
5. Separate visibility overlays from follow/movement policy.
6. Do not treat the current single-monitor fallback as proof of interactive same-monitor magnification.
7. Keep WGC/D3D11 as the default graphics path, not a universal guarantee. Make GPU/device ownership explicit.
8. Do not carry the present-wide graphics mutex unchanged into multi-output.
9. Improve raster reconstruction before committing to semantic text rendering.
10. Promote lifecycle/recovery, compatibility and accessible configuration.
11. Begin low-vision/assessor evidence early and in parallel.
12. Expect substantial Windows/app compatibility burden despite narrower feature scope.

## 2. Newly elevated issues

- Current display-topology changes terminate Vision; in-process reconciliation must be part of the multi-view lifetime model.
- The generalized view model needs an explicit geometry/magnification contract for unequal source/destination sizes, portrait displays and partial destinations.
- Current telemetry/acceptance claims need a stricter replay/baseline oracle before structural changes are called behaviour-preserving.
- Ctrl+Alt global hotkeys require an AltGr collision check on European layouts.
- Vision's own settings/help UI needs DPI/text-scale-aware layout before settings complexity grows.
- Real pointer-shape handling deserves explicit product evaluation.
- Windows Magnifier must be part of the comparator set as the free baseline.
- Persistent user intent must be separated from resolved current topology.

## 3. Material differences and resolution

### GPU/device model

Opus: one shared D3D11 device behind a GpuContext; split only if measurement requires it.  
Astra: explicit device domains, initially one; do not make one global device a permanent invariant.

**Resolution:** use explicit device-domain ownership, with one domain initially.

### Tethered/context-relocation seam

Opus rejects reserving a named Tethered-style seam because app semantics create support burden. Astra preserves generic dimensions for source region, update policy and destination placement.

**Resolution:** do not reserve a named Tethered subsystem. Preserve generic region/update/placement primitives only.

### Same-monitor timing

Opus makes the same-monitor spike the highest-value gate before Stage 3. Astra makes it blocking only if initial architecture promises interactive self-magnification.

**Resolution:** not a blocker for the first extraction slices; it gates first-class same-monitor/self-magnification support.

### Pre-implementation blockers

Both require a trustworthy unchanged-build baseline/replay before claiming behaviour-preserving refactor. Astra additionally elevates explicit geometry semantics.

**Resolution:** before structural refactor require:
1. a trustworthy replay/baseline oracle;
2. an explicit geometry contract.

Lifecycle, identity, fan-out/pacing and same-monitor experiments gate the slices that depend on them rather than the initial extraction.


## 4. Revised architecture direction

The combined review supports these conceptual responsibilities:

- **MonitorRegistry / TopologySnapshot:** current topology, generations, identity hints and diffs.
- **GpuDeviceDomain:** explicit D3D11/WinRT device domain; one domain initially.
- **CaptureSource:** source lifecycle and owned latest-frame/cache state.
- **EvidenceSampler:** global evidence acquisition only; no view movement decisions.
- **WorkspaceCoordinator:** resolved workspace, active movement owner, routing, arbitration, command targeting and topology rebuild policy.
- **ViewSession:** source/destination binding, viewport/return state, visual state and overlays.
- **OutputPresenter / ViewRenderer:** destination surface, presentation scheduling, reconstruction, colour and overlays.

Important invariants:

- evidence is global; relevance and movement permission are not;
- saved workspace intent is separate from current resolved topology;
- visibility and following are independent;
- frame/evidence/topology generations are explicit;
- a slow output cannot block capture or other outputs;
- geometry semantics are explicit rather than inferred from matched monitor sizes.

## 5. Renderer decision after independent review

Both reviewers validate the staged direction but sharpen it:

1. define/fix geometry and pixel mapping first;
2. compare a small number of controlled raster reconstruction options against current bilinear scaling;
3. evaluate static text and moving/scrolling text, including ClearType/subpixel artefacts;
4. only if best raster remains inadequate at real working zooms should targeted semantic enhancement or clean-text assistance be promoted.

The earlier ZoomText comparison remains useful evidence of the problem, but not evidence of raster reconstruction's ceiling.

## 6. Development-sequence correction

Recommended sequence after review:

1. **Baseline/replay oracle + geometry contract.**
2. Extract one current view's state/evidence/update responsibilities without changing behaviour.
3. Extract explicit GPU/output/capture lifetimes; remove present-wide blocking.
4. Introduce WorkspaceCoordinator and explicit view identity.
5. Add monitor/topology identity and preserve intended workspace separately from resolved topology.
6. Replace exit-on-display-change with debounced in-process reconciliation.
7. Add one-source-to-two-output scaling test, then a second source.
8. Introduce active-owner transfer and decoupled overlays as explicit behaviour changes.
9. In parallel: raster filter study, AltGr check, DPI-aware UI/localisation preparation, Windows Magnifier comparison and early low-vision/assessor sessions.
10. Gate same-monitor first-class support on its dedicated interaction spike.
11. Only then expand product modes/features from demonstrated user-task failures.

## 7. Review-specific findings worth carrying forward

From Opus:
- current pointer samples are dropped when leaving the source, which likely contributes to the known boundary jump;
- current overlay rendering is coupled to the winning follow candidate;
- real pointer shape, zoom beyond 4x, start-at-sign-in and AltGr-safe hotkeys deserve explicit evaluation;
- exit-on-topology-change is unacceptable as the long-term lifecycle model.

From Astra:
- unequal source/destination geometry exposes a deeper zoom-contract problem than monitor enumeration alone;
- saved intended workspace and resolved current topology must be separate;
- current telemetry fields can overstate what some acceptance runs prove;
- source/view/frame/topology generations should become explicit diagnostic state;
- capability gating is preferable to pretending same-monitor, HDR or cross-adapter behaviour is universally supported.

## 8. Decision boundary

The independent reviews **support starting architecture extraction**, but not by immediately implementing the previously proposed full 2-4-monitor object model.

The first implementation should be a narrow extraction of the current validated relationship, protected by replay/acceptance evidence and an explicit geometry contract. Multi-view breadth is added only after those responsibilities and lifetimes are real.
