# Prompt for Opus: independent review of Vision product scope and architecture

## Role

Act as an independent senior product/architecture reviewer. Do not merely improve the proposed plan. Try to falsify it, identify hidden assumptions, and propose materially better alternatives where justified.

The project is **Vision**, a Windows low-vision magnification application. The Doxa hardware installer is a separate workstream and is not part of this architecture review except where generic Vision must later run correctly on Doxa displays.

Do not write implementation code. Do not produce a pricing strategy. The task is to assess the evidence, proposed product boundary, feature priorities, architecture direction and development sequence **before implementation starts**.

## Fixed programme decisions for this review

- Vision should be hardware-agnostic and should ultimately support ordinary Windows systems with 2, 3 or 4 monitors. Doxa is a later qualified hardware configuration, not a separate Vision fork.
- The Doxa installer/hardware setup is independent and currently waits for real SM770 hardware.
- Broader non-low-vision Doxa software opportunities are parked.
- English is the initial product language, but localisation readiness should be designed before UI breadth expands.
- No proprietary source/code/assets from ZoomText or SuperNova may be used. Competitor research is limited to public material and legitimate black-box observation.
- Do not assume feature parity is the target.
- Pricing strategy and final route to market are deliberately postponed until after this review and later dealer/assessor evidence.

## Current evidence boundary

The current two-screen Vision alpha is real and tested. It already has WGC capture, D3D11 rendering, pointer/caret/focus evidence, POI arbitration, viewport control, Context + Detail, View Locator, 1x/return, colour modes, settings, install/update/diagnostics and an acceptance harness.

However, current runtime architecture is still essentially one physical source monitor -> one CaptureRunner -> one Renderer/Detail window, plus an optional untouched Reference display. It enumerates N monitors but is not yet a genuine N-view architecture.

The Dell black-box bench now contains common pointer, caret, focus and cross-monitor runs for Vision, ZoomText 2026 and SuperNova Magnifier 25.05, plus an installed SuperNova menu inventory and targeted feature research. Treat the common workload runs and installed menu inventory as hands-on evidence. Treat vendor-documented feature semantics as external evidence, not proof that every scripted setting change was observed live. The main unresolved technical experiment is matched Office text quality: SuperNova uses TrueFonts real-font substitution where supported and Standard smoothing in hardware-accelerated browsers, while ZoomText xFont is on by default in supported Office apps. Exact matched Vision-vs-incumbent Office rendering remains insufficiently controlled.

## Questions you must answer

### A. Product boundary and feature strategy

1. Is the proposed first product boundary - magnification-first for users with useful functional vision, excluding full screen-reader/Braille parity - coherent technically and commercially? What evidence would falsify it?
2. Does the feature-priority matrix correctly identify the few capabilities likely to deliver most user value? Identify any feature we have overvalued, undervalued or omitted.
3. Is Context + Detail a meaningful product advantage, merely one preset among several, or a distraction from more universal magnifier behaviour?
4. Which incumbent capabilities are likely to be table stakes in dealer/assessor evaluations even if day-to-day usage is lower?
5. How should basic speech/read-aloud be treated: architectural seam only, early optional capability, or outside initial scope?

### B. 2-4 monitor architecture

6. Critique the proposed separation into MonitorRegistry, CaptureSource, shared EvidenceHub and per-output ViewSession. Is this the minimum clean model, or is it over/under-abstracted?
7. The current code tightly couples WGC, evidence sampling, ViewController and Renderer inside one CaptureRunner. Propose the safest incremental extraction sequence that preserves the current validated two-screen behaviour after each step.
8. For multiple concurrent views, should Vision share one D3D11 device/capture texture domain with per-view swap chains, or use more isolated per-view devices/renderers? Address hybrid/multi-adapter machines, WGC interop, resource sharing, failure isolation and performance.
9. Should evidence sampling be global/shared or scoped per source/view? How would you prevent a semantic caret/focus event on one monitor from moving the wrong magnified view?
10. Is same-monitor magnification (A -> A) robust enough to make first-class alongside cross-monitor magnification (A -> B), given capture-exclusion/recursion risks?
11. How should Vision model monitor identity and topology across reboot, docking, port changes, EDID ambiguity, hot-plug and mixed DPI?
12. What workspace/configuration schema is the minimum that can cleanly express 2, 3 and 4 monitors without prematurely encoding every ZoomText/SuperNova clone/span/presentation mode?

### C. Tracking, text quality and compatibility

13. Evaluate the proposed pointer-boundary policy: hold the pointer-driven view when the pointer leaves its source, then release on pointer return or fresh strong semantic intent. What failure modes or better alternatives exist?
14. Is the current WGC + raster crop/scale architecture likely to deliver acceptable text quality for a focused product at typical low-vision zoom levels, or is text smoothing/semantic re-rendering likely to become a fundamental architecture change?
15. Give a staged way to resolve the xFont/True Fonts question without prematurely building a semantic text renderer.
16. What application compatibility matrix and regression architecture is necessary before Vision can credibly claim workplace usefulness?

### D. Localisation and product engineering

17. Should localisation readiness be introduced before, during or after the architectural extraction? Is a lightweight string catalogue enough for the current native Win32 UI?
18. What current technical debt would become disproportionately expensive once the product gains more views, features and languages?
19. Which architectural seams should be deliberately left open for later profiles, pinned regions, clone/presentation, reading modes or basic speech - and which should NOT be designed now?

### E. Commercial/product implications without setting price

20. The incumbents bundle compatibility maintenance, support, training/channel familiarity and enterprise deployment. Does the proposed smaller product genuinely reduce lifetime cost, or are we underestimating the support burden?
21. Which capabilities are commercially important because they reduce dealer support or unlock workplace procurement, even if they are not daily-user features?
22. What evidence should we obtain from dealers/assessors before choosing a pricing strategy or route to market?
23. What is the strongest plausible entry wedge for Vision, and what would make that wedge fail?

## Required output

Produce a decision-oriented review, not a generic brainstorm.

1. **Executive assessment** - the 5-10 conclusions that most change or validate the proposed direction.
2. **Critical challenges** - assumptions that are weak, contradicted, under-evidenced or likely to create expensive rework.
3. **Feature-scope corrections** - must-have, defer, drop/rethink, and missing capabilities. Do not reproduce the existing matrix unchanged.
4. **Architecture review** - recommended conceptual model, major alternatives, failure modes and the safest incremental migration from the current two-screen code.
5. **Text-quality decision path** - experiments/evidence required before committing to a rendering strategy.
6. **2-4 monitor model** - minimum configuration semantics and interaction policy required for a coherent product.
7. **Localisation recommendation** - what must be changed early and what can wait.
8. **Commercial implications** - what the technical/product choices imply for supportability and dealer acceptance, without selecting a price.
9. **Pre-implementation experiments** - the smallest set of experiments or hands-on competitor tests that must be completed before architecture implementation, ranked by decision value.
10. **Revised development sequence** - only if you believe the proposed sequence should change, explaining why.
11. **Verdict by decision** - for each major proposal, classify it as `Keep`, `Modify`, `Reject`, or `Insufficient evidence`, with concise rationale.

Be explicit about uncertainty. Distinguish repository facts, external evidence, inference and recommendation. Do not invent competitor internals, dealer margins, market share, or user behaviour that is not supported by evidence.

## v0.2 mandatory review additions

The wider incumbent sweep materially changes the feature questions. Address these explicitly in addition to the numbered questions above:

- Should visual locator/highlighting be a first-product core subsystem rather than a later UI refinement?
- Is the proposed separation between POI/viewport policy and visual-overlay policy correct? Where should overlay state live in a multi-view architecture?
- What minimal locator preset set would cover the orientation problem without recreating incumbent customisation complexity?
- Does a one-monitor Vision need at least one lens/fixed/contextual mode even if multi-monitor Context + Detail is the main differentiator?
- How should Vision model monitor-scoped visual effects when SuperNova and ZoomText both support display-specific enhancement behaviour?
- Does the incumbent use of real-font substitution in Office change the acceptable architecture risk for Vision, or can a staged raster/sharpening strategy remain the default until evidence proves otherwise?
- Should application-scoped overrides be represented in the first versioned settings/workspace schema even if the UI for profiles is deferred?
- Which installed SuperNova Magnifier features are genuine table stakes for a magnifier-only product versus breadth that Vision should deliberately omit?

When evidence is insufficient, say exactly which smallest experiment would resolve the decision. Do not convert every unresolved point into a prerequisite if it can safely remain a staged validation.
