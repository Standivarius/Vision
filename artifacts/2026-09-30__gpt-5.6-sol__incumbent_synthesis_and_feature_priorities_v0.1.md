# Vision incumbent synthesis and feature priorities v0.1

**Date:** 2026-09-30  
**Status:** pre-Opus synthesis; product/architecture recommendations, not implementation approval  
**Primary evidence:** current Vision repo/foundation docs; comprehensive ZoomText 2026 assessment; comprehensive SuperNova Magnifier 25.05 assessment; earlier common hands-on tracking runs; user 2x/4x Word text-quality observations.

## 1. Executive synthesis

The combined incumbent evidence does **not** support feature parity as Vision's strategy.

It does support a focused first product with six deep quality pillars:

1. **magnification/rendering quality** good enough that text is not a competitive disadvantage;
2. **orientation** through pointer/caret/focus visibility aids and fast context recovery;
3. **predictable tracking and viewport behaviour**, including conflict handling;
4. **coherent multi-monitor behaviour** with independent per-view state and explicit active-view/crossing policy;
5. **context preservation** through Context + Detail now and carefully chosen pinned/relocated context later;
6. **supportability**: persistence, install/update, diagnostics, contextual help and compatibility evidence.

The mature products are broad because they accumulated many user segments over time. Their breadth is evidence of problems that exist, not evidence that Vision must solve all of them in version 1.

## 2. What the incumbent research changed

### 2.1 Orientation is first-product core

Earlier Vision planning risked treating highlighting/locator treatment as polish after tracking. ZoomText and SuperNova both invest heavily in pointer, caret and focus visibility because successful tracking does not by itself tell the user where to look.

Vision already has the evidence and overlay foundations. The missing work is mainly productisation: a small number of strong presets, consistent geometry, per-view policy and validation.

### 2.2 Multi-monitor requires interaction policy, not just more render targets

Both incumbents expose multi-monitor behaviour as a user model, not simply output count.

The critical new ZoomText challenge is **active-view ownership**: MultiView can keep independent view state while only one view is actively moving at a time, with ownership transferred explicitly or through activity crossing desktops.

SuperNova adds **boundary policy** evidence through Mouse Buffer, monitor switching, independent per-monitor zoom/colour and Side-by-Side/clone patterns.

Therefore Vision's proposed `CaptureSource + ViewSession + shared EvidenceHub` direction remains credible, but a shared evidence service must not imply that every view independently follows every fresh signal.

## 3. Product scope after reconciliation

### Core / first product

- high-quality magnification with 1x, 1.5x, 2x, 3x, 4x and exact temporary-normal/return;
- pointer, caret and keyboard-focus evidence with selective following;
- viewport dead zones/margins/hysteresis/panning and clear conflict policy;
- pointer/caret/focus visibility layer with a small preset family;
- persistent Context + Detail and View Locator;
- generic 2-4 monitor model with independent per-view zoom/visual state;
- explicit active-view and monitor-crossing policy;
- simple colour/contrast/tint controls and a few useful presets;
- Office/browser/common-Windows compatibility work;
- persistence, topology recovery, installation/update/diagnostics;
- contextual help and incumbent-terminology translation;
- text quality that is competitive at common working magnifications.

### Preserve seams; validate later

- one single-monitor contextual/lens/fixed view;
- Freeze/Hooked-Area-style pinned region/reference view;
- Tethered-style dynamic context relocation;
- simple application-scoped overrides;
- clone/standard-view collaboration;
- presentation/share-safe mode;
- optional clean-text/Live-Text-style view;
- basic reading assistance if user evidence promotes it.

### Deliberately defer

- Span as a product pillar;
- large colour/pointer/highlight catalogues and custom editors;
- deep Situation Settings automation;
- full Reader/AppReader/OCR workflow;
- touch-first features;
- camera/whiteboard/media ecosystems;
- broad speech/screen-reader/Braille parity.


## 4. Architecture implications

### 4.1 Keep Source -> Evidence -> View -> Destination separation

The current engineering principle remains sound:

`Source -> Point of Interest evidence -> View transformation -> Destination`.

Capture should not own viewport policy. Evidence collection should not own active-view policy. Overlay rendering should not be hidden inside POI selection. This separation is strengthened, not weakened, by the incumbent evidence.

### 4.2 Modify the shared EvidenceHub proposal

A central evidence sampler remains attractive for cost, consistency and diagnostics, especially for UIA/Win32 evidence that should not be duplicated per output.

However, the hub should publish **evidence**, not decisions.

Each view/workspace policy needs to decide:

- whether that evidence is relevant to its source;
- whether the view is currently eligible to move;
- whether it owns active-follow responsibility;
- whether crossing another monitor transfers ownership;
- whether a pointer-leave state should hold the current viewport;
- whether stronger caret/focus evidence can override that hold.

An explicit active-view/ownership controller may therefore sit above or beside ViewSessions. Opus should challenge whether this is a separate subsystem or simply policy state within a workspace.

### 4.3 Per-view overlays should be independent of viewport motion

Pointer/caret/focus visibility should be attributable to a view/destination and should remain configurable even when following is disabled.

That allows states such as:

- show pointer locator but do not move viewport;
- show caret highlight while Context remains static;
- use a stronger locator on one display and a lighter one on another;
- expose boundary/monitor-switch cues without changing capture.

The current basic overlay implementation is therefore a useful foundation, but overlay state should become explicit per-view state as the architecture generalises.

### 4.4 Context aids are a family, not one feature

SuperNova Overview, split/lens modes, Margin Release and Hooked Areas plus ZoomText Freeze/Tethered/Live Text show several distinct ways to reduce context loss.

Vision should keep these concepts separate:

- **overview/context view**: broad spatial orientation;
- **temporary normal/return**: momentary recovery;
- **pinned/frozen region**: persistent reference;
- **dynamic context relocation**: task-relevant remote content moved near the work locus;
- **clean text view**: semantic/readability fallback.

The first product needs the first two. Architecture should preserve a path to the others without prebuilding them.

## 5. Renderer decision after hands-on comparison

The earlier plan treated text quality as a binary architecture gate: remain raster-based or introduce semantic text re-rendering.

The evidence now supports a narrower decision.

### Established from current evidence

- current Vision 4x is visibly softer than ZoomText;
- ZoomText xFont at 2x was judged smooth and natural;
- ZoomText 4x stays crisp at the edge but introduces glyph-shape distortions;
- ZoomText itself needs geometric-smoothing fallbacks and per-app exclusions;
- SuperNova also treats font rendering quality as a dedicated subsystem rather than evidence that all content can be semantically reconstructed.

### Revised working target

Vision should aim for:

- **1x-2x:** essentially native-looking or close enough that text quality is not a reason to abandon Vision;
- **2x-3x:** at least competitive perceived quality with ZoomText in normal office work;
- **4x+:** substantially crisper than current Vision while preserving glyph geometry and avoiding obvious local distortions.

### Revised architecture hypothesis

Keep the WGC/D3D11 capture path as the universal baseline. Improve reconstruction/sharpening in the normal GPU pipeline first. Preserve an interface for targeted semantic text enhancement or a clean-text view later, but do not make universal semantic re-rendering a prerequisite for the multi-view refactor.

The matched 2x Vision-vs-ZoomText comparison remains a useful release-quality experiment, but no longer needs to block the independent architecture review.

## 7. What Vision should try to outperform

Vision does not need to beat the incumbents at accumulated feature count.

It should try to outperform them on:

- multi-monitor clarity and predictability;
- stable Context + Detail workflow;
- temporary inspect/normal/return;
- explicit monitor roles rather than opaque mode combinations;
- simpler orientation aids with strong defaults;
- understandable crossing/ownership behaviour;
- low-friction setup and recovery;
- contextual assistance that explains what to do next without requiring specialist terminology.

Text quality is different: Vision does not need to invent the most sophisticated typography system, but it must be good enough that users do not reject the workflow because reading is visibly worse.

## 8. Evidence boundaries carried into Opus

Still unresolved and important:

- physical 3/4-monitor performance and interaction;
- final stable monitor-identity strategy, especially identical panels;
- cross-adapter/USB display behaviour;
- user preference for active-view ownership versus more independent following;
- matched 2x Vision-vs-ZoomText perceived text quality;
- actual low-vision user value of pinned/frozen and Tethered-style workflows;
- compatibility breadth across Word, Excel, Outlook, Edge/Chrome, Teams/Electron and specialised apps.

These should not all become pre-implementation blockers. Opus should identify which decisions truly require evidence before architecture extraction and which can remain staged validation gates.

## 9. Recommendation entering independent review

The current strategic direction should enter Opus as **provisionally supported but materially modified**:

- keep WGC/D3D11 and the Source/Evidence/View/Destination separation;
- keep generic 2-4 monitor scope;
- keep Context + Detail as the default differentiating workflow;
- keep per-view state and source reuse;
- **modify** the shared EvidenceHub concept so it cannot imply global follow behaviour;
- add an explicit active-view/crossing policy question;
- promote orientation overlays into first-product core;
- narrow the renderer gate to staged quality improvement rather than universal semantic rendering;
- preserve seams for contextual/frozen/clean-text/app-scoped features without implementing them during the architecture extraction.

This is now sufficient input for an independent Opus product/architecture review.
