# Distribution/support stack and Doxa research directions v0.1

**Date:** 2026-09-23
**Project:** Visual / Doxa

## Distribution/support: adopt rather than build

### Best current fit for Visual application packaging/update

**Velopack** is the strongest current candidate for the native C++ Visual application.

Reasons:

- MIT-licensed open source;
- explicit C/C++ library/API support;
- creates Windows installer and update packages from compiler output;
- supports semantic-versioned releases;
- supports automatic update checks/download/apply/restart;
- can host update payloads on GitHub Releases, static web storage, S3-like storage, etc.;
- supports per-user one-click Setup.exe without elevation;
- can also generate MSI/per-machine deployment later if needed;
- delta updates reduce update download size.

This would allow Visual to avoid building its own version/update subsystem.

### Early release hosting

**GitHub Releases** is sufficient for development and early external testing. Release assets can carry installers/update payloads and have no aggregate bandwidth limit in GitHub's documented release-asset model (individual assets must be under the per-file limit).

WinGet can be considered later for a broadly distributed generic Visual package, but is not necessary for the Doxa-first product.

### Windows trust / signing

Packaging software does not remove the need for trusted code signing for public direct distribution.

Microsoft currently recommends Azure Artifact Signing for non-Store distribution. Basic pricing is approximately US$9.99/month with 5,000 signatures/month. Organization availability includes the EU; individual geographic eligibility is more limited. Traditional OV certificates are the alternative.

Microsoft Store distribution can avoid separate signing cost for MSIX packages, but Store distribution is not currently the primary Doxa scenario.

### Doxa hardware installer boundary

Do not make Velopack responsible for unverified hardware-driver/firmware operations.

If Doxa later requires a signed vendor driver, firmware package or elevated machine-wide dependency, keep that as a separate Doxa setup/bootstrap layer that invokes the vendor-supported package. Determine this only after the actual Doxa controller/package model is known.

Inno Setup is capable and scriptable but now requests paid commercial licensing; WiX is powerful but has an open-source maintenance-fee model for revenue users. Neither needs to be introduced yet.

## Diagnostics/support: minimal adoption stack

### Local diagnostics

Visual still needs a small deterministic local diagnostics command/tool because no generic support platform knows Visual-specific facts such as WGC state, monitor topology, POI provider health, frame cadence or Doxa role mapping.

The output should be structured JSON/text rather than an LLM having arbitrary shell access.

### Telemetry

OpenTelemetry C++ is mature enough for application metrics/logs/traces (current C++ traces, metrics and logs marked stable). It can standardize telemetry without locking the app to one backend.

For native crashes, Chromium Crashpad is an open-source option that captures/stores/transmits minidump crash reports. Crash-upload privacy/consent needs explicit product design.

GlitchTip is a lightweight open-source Sentry-compatible error-monitoring backend, but native crash-dump compatibility should be validated before depending on it for C++ crash capture.

### Human remote support

**RustDesk OSS** is a strong low-cost option for opt-in remote support. It supports Windows clients and a self-hosted open-source relay/signaling server. It can provide a technician with remote desktop control without building remote-support infrastructure.

**MeshCentral** is another open-source choice if future needs expand toward managed fleets, remote terminal/file management and persistent device administration. It is heavier than needed for early Doxa support.

### LLM support

Do not build an LLM orchestration system.

**Dify** is a strong open-source candidate for a later support assistant: visual workflow construction, RAG/knowledge documents, model-provider abstraction, tool/function calling and API access.

Initial safe use:

1. Visual diagnostics generates a support bundle;
2. user/support technician uploads or attaches it to the support assistant;
3. Dify/RAG gives the LLM product docs, known issues and approved troubleshooting procedures;
4. LLM explains likely cause and recommended approved action;
5. if unresolved, escalate to a human using RustDesk.

Do not initially give the LLM unrestricted administrator/shell access.

Chatwoot can be added later as a ticket/chat front-end. Its self-hosted Community Edition is free, but its built-in Captain AI is a paid self-hosted feature, so Dify + a simple support UI is likely cheaper initially.

## Minimal stack recommendation

For the POC / first Doxa pilots:

- Visual.exe: current C++ app;
- packaging + auto-update: Velopack;
- releases: GitHub Releases;
- signing when external distribution begins: Azure Artifact Signing if eligible, otherwise OV certificate;
- diagnostics: small Visual-owned structured diagnostics tool;
- remote support: RustDesk OSS;
- LLM: defer, then use Dify around diagnostic bundles and knowledge base;
- telemetry: retain current local logs first; introduce OpenTelemetry when field deployments justify centralized observability.

This avoids building an installer engine, updater, release server, remote desktop product, ticketing system or LLM orchestration layer.

## Low-vision research: first web-pass conclusions

### Strong evidence

1. **Magnification creates context and navigation costs.**
   Studies of low-vision users in Office and web tasks report substantial panning/refocusing/zoom adjustment and difficulty comparing spatially separated information.

2. **Automatic/assisted tracking is valuable.**
   Office-magnifier research found benefit from keeping the magnifier viewport synchronized with keyboard-caret activity.

3. **Context + detail is promising but has a visual-load trade-off.**
   A 2026 CHI study with low-vision participants found a dynamic context technique improved access/usability/effort while increasing visual load; a minimap supported spatial understanding but was less preferred for that task.

4. **Viewing distance is a major variable.**
   Survey evidence from 75 adults with low vision found that users obtain magnification through both increased physical character size and reduced viewing distance, with low-vision computer reading distances substantially shorter than normally sighted controls.

5. **Individual strategies vary materially.**
   A 2023 study of 20 low-vision magnifier users found no universal winner between full-screen and lens modes and observed individual preferred screen regions/motion patterns.

### Plausible but not established for low vision

**More screens improve productivity.**

General multi-monitor research and systematic reviews support preference and some task-efficiency gains, but also identify neck/postural costs. The initial search found little direct empirical work testing 2-vs-3-vs-4 monitor configurations specifically for low-vision magnifier users.

Therefore Doxa's 'magnification + productivity from persistent information exposure' proposition is a high-value hypothesis, not an established fact.

### Directly relevant adjacent evidence

- General multi-monitor field work finds secondary displays often used for peripheral awareness and easy access to reference/background information rather than as equal primary workspaces.
- A systematic review of 18 multiple-monitor studies found moderate evidence of improved task efficiency/decreased desktop interaction and evidence of non-neutral neck posture risks.
- Current ZoomText includes Freeze Views and multiple-monitor modes specifically to preserve important content while the main magnified view moves; this is product precedent rather than controlled evidence.

## Recommended deep-research directions

Organize the deep research around four questions, not around specific proposed Doxa screen roles.

### R1 — What costs does magnification impose on productive computer work?

Investigate:

- panning/refocusing;
- zoom readjustment;
- comparison across separated content;
- ribbons/toolbars/menus outside viewport;
- cursor/caret loss;
- working-memory/spatial-orientation burden;
- application switching.

Tasks: writing/editing, spreadsheets, forms/data entry, browser research/comparison, communication while working.

### R2 — Can persistent spatial context reduce those costs?

Investigate empirical evidence for:

- overview + detail;
- focus + context;
- freeze/reference areas;
- secondary stable displays;
- side-by-side comparison;
- compacting/rearranging information versus magnifying more screen area.

Key question: which navigation costs could Doxa replace with glanceable stable information?

### R3 — What is the productivity/ergonomics trade-off of more displays?

Compare evidence for:

- one vs two vs three vs four displays;
- task performance and switching;
- visual search;
- head/neck rotation;
- vertical gaze switching;
- fatigue;
- monitor angle and distance.

Separate low-vision-specific evidence from general-population multi-monitor evidence.

### R4 — Which functional-vision/person variables alter the optimum?

Investigate:

- central vs peripheral field loss;
- acuity and preferred angular print size;
- viewing distance;
- contrast/glare sensitivity;
- motion/clutter sensitivity;
- preferred magnification level/mode;
- mouse vs keyboard workflow;
- habitual strategies and learning effects.

Avoid assuming medical diagnosis alone predicts the right workspace configuration.

## Proposed Deep Research deliverable

Ask ChatGPT Deep Research to produce:

1. evidence map with source quality and participant counts;
2. findings separated into established / suggestive / unknown;
3. explicit evidence for or against the Doxa hypothesis that persistent extra screen space can reduce magnification-navigation cost;
4. ergonomics risks of 3-wide upper row plus laptop-below geometry;
5. user/task variables likely to modify preferences;
6. competitor/user-workflow evidence clearly separated from controlled studies;
7. a prioritized set of experiments to run when the Doxa unit arrives;
8. interview/usability-study questions suitable for low-vision participants;
9. no premature recommendation of fixed screen roles unless supported by evidence.
