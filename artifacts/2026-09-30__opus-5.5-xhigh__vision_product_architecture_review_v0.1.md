## 1. Executive assessment

1. **The direction is broadly right, but the plan puts multi-view breadth ahead of two gaps that matter more: surviving real display lifecycles, and any low-vision user evidence at all.** Today, any `WM_DISPLAYCHANGE` destroys the Detail window and exits with code 12, and nothing relaunches Vision (`main.cpp:1004-1007`) [R]. Monitor sleep/wake is not validated (README "Known limitations") [R]. No low-vision user or assessor has used Vision on a task; the roadmap still lists "human low-vision tuning" and "Context+Detail productivity comparisons" as future work [R]. For a low-vision user, a magnifier that silently disappears when a screen sleeps or a laptop docks is a severe failure. Moving to 3–4 monitors makes these events more frequent [I]. **Handling topology changes inside the running process belongs in the extraction, not after it.**
2. **Keep the Source → Evidence → View → Destination split, but the proposed four objects leave out the piece that actually holds today's coupling: a workspace coordinator.** The per-tick loop in `CaptureRunner::render_loop` (sample → filter → arbitrate → update viewport → pick locator → publish → render, `main.cpp:726-780`) plus the process-global view state (`main.cpp:66-89`) is that coordinator. It should be extracted and named, not spread across an "EvidenceHub" and N ViewSessions [Rec].
3. **Active-view ownership: adopt one active follow owner, handed over by the user's latest activity and routed by geometry. Implement it as policy state inside the coordinator, not as a separate subsystem.** Hotkeys and commands need a target view whatever the follow model is. Global "intent barriers" (the pointer moved after the caret changed) need knowledge across views. With views partitioned by source, "independent following" and "single owner" differ only in rare cases, so the single-owner rule costs almost nothing and makes behaviour deterministic [I/Rec].
4. **The known boundary jump is an architecture defect, not a UX detail, and the extraction fixes it almost for free.** Pointer samples outside the source are discarded at sampling time (`win32_evidence_provider.h:56`). That disables the pointer intent barrier in `select_best_poi` (`poi_evidence.h:103-112`) exactly when the pointer leaves the source [R]. This is consistent with the documented jump [I]. Sampling globally and routing afterwards restores the barrier, so the hold-on-leave behaviour follows naturally.
5. **Separating overlays from arbitration is justified by a defect in the current build, not just by architectural tidiness.** Candidates are removed by *follow* settings before arbitration, and a locator is drawn only for the *selected* POI (`main.cpp:742-755`) [R]. So a caret highlight cannot appear while caret following is off, and only the winning target is ever marked [I from code; verify with a unit test]. That contradicts README's "independent" controls claim.
6. **"Same-monitor magnification as first-class" is not supported by evidence.** The single-monitor fallback is a 45%-size, captioned, topmost window with capture exclusion (`main.cpp:1038-1063`) [R]. It proves capture exclusion only. Full-screen self-magnification would additionally need click-through input to line up with what is shown, hiding the system cursor, and staying on top of shell surfaces (Start, Alt+Tab, notifications) without UIAccess. Your own 2026-09-19 adversarial review flagged exactly this and recommended a separate spike that may pick a different backend; that spike was never run [R]. The Magnification API full-screen transform takes a single factor and offset for the whole desktop [D], so it cannot deliver independent zoom per monitor. **This is the highest-value experiment before Stage 3.**
7. **The renderer's staged approach is right, but the comparison it rests on used the weakest possible baseline.** Vision samples with plain bilinear filtering (`D3D11_FILTER_MIN_MAG_MIP_LINEAR`, `main.cpp:578`) in one pixel shader that also does colour and locators [R]. "Vision is softer at 4x" is the expected result of bilinear magnification. It is not evidence about raster reconstruction's ceiling [I]. The first renderer step is a cheap offline filter comparison that needs no architecture. The xFont judgement also comes from one non-target-user observer (the owner, partly from phone photos), so semantic enhancement should stay an open, evidence-gated option rather than a rejected one [I].
8. **The product boundary (magnifier-first, no screen reader or Braille) makes sense, but the comparator set is missing the free baseline, Windows Magnifier** (full-screen/docked/lens views, smoothing, invert, follow mouse/focus/caret, read-aloud), plus Windows 11's own pointer and text-cursor indicators [D]. An assessor's first question about a cheaper product will be "why not Windows Magnifier plus a second monitor?" The wedge has to answer that, and research never measured it [I].
9. **Several first-product gaps are missing or underrated.** Rendering the real pointer *shape* in Detail (today Detail shows only a crosshair because cursor capture is off, `main.cpp:654`, `528-536` [R]). Zoom capped at 4x (`settings_model.h:35` [R]), which likely rules out a real part of the functional-vision segment [U]. Vision's own UI uses fixed pixel fonts and layouts with no DPI handling (`settings_window.cpp:183`, `255-295` [R]). Ctrl+Alt global hotkeys, including Ctrl+Alt+Q = exit, very likely fire on AltGr characters on European layouts, e.g. German AltGr+Q = "@", Romanian (Programmers) AltGr+S/T/Q = ș/ț/â [D: AltGr is treated as Ctrl+Alt; verify on-device]. No start-at-sign-in option [R].
10. **A smaller product does not buy a proportionally smaller compatibility burden.** Tracking, capture and topology compatibility is driven by the environment (Windows, Office, Chromium and GPU-driver updates), not by feature count [I]. The real saving comes from **not hooking into applications**: no app-injected text re-rendering and no screen reader. Every semantic or app-specific integration (xFont-like text, Tethered View, app profiles) brings back incumbent-class maintenance. That is the strongest argument for keeping semantic work narrow [I].

## 3. Product-scope corrections

**First-product must-have (additions or promotions marked ▲):**
- ▲ In-process topology reconciliation: sleep/wake, dock/undock, hot-plug, resolution/DPI change, without exiting. Plus an optional start-at-sign-in and a guaranteed-recoverable launch path.
- ▲ Real pointer shape (arrow / I-beam / hand / busy) drawn scaled at interaction cadence in magnified views, with an optional size boost. The crosshair becomes a locator preset, not the pointer.
- ▲ Pointer-leave hold (fixes the known defect) and a visible boundary cue.
- ▲ Overlay decoupling: pointer, caret and focus marks shown independently of following.
- ▲ Zoom range extended pragmatically (at least 6–8x plus fractional steps), gated on reconstruction quality at those levels [U: need the target-user zoom distribution].
- ▲ Vision's own UI: DPI and text-scale aware, keyboard-complete, hotkeys free of AltGr collisions.
- Kept from the proposal: tracking and viewport policy (**add easing/smoothing**: `view_controller.h` currently steps straight to the target [R]); temporary 1x/return; View Locator; small preset set; colour/contrast plus brightness/tint; per-view zoom and visual state; bounded compatibility; install/update/diagnostics; contextual help.

**Preserve as structural seam only (no fields or UI yet):** views as a *list*; destination geometry (full now, rect later); optional source sub-rectangle plus live/frozen flag (Freeze/Hooked-area path); settings read through a resolver function (app-scoped overrides later); the view transform exposed to a composition stage (targeted text enhancement later).

**Defer / drop as seams:** Tethered-style relocation (no reservation), clean-text/Live Text (leave undefined), clone/presentation (expressible already as two views of one source, so nothing to reserve), Span (excluded), Situation Settings, reading suite, OCR, camera, touch, secure/logon parity. For sign-in and UAC magnification, document Windows Magnifier as the fallback.

**Missing capabilities to evaluate (not yet commitments):** a Windows Magnifier comparison; basic read-aloud (the Magnifier/Reader tier exists and Windows Magnifier includes reading [D]; decide via assessor evidence); a "Detail screens are not pointer destinations" rule for Context+Detail (see §5).

## 4. Architecture recommendation

**Minimum clean model.** Seven responsibilities, but three of them are simply the current `Renderer` and `render_loop` given names, not new layers:

| Responsibility | Owns | Does **not** own | Extracted from |
|---|---|---|---|
| **MonitorRegistry** | QueryDisplayConfig/GetMonitorInfo enumeration, fingerprints, `TopologySnapshot` + diffs, debounce | roles, views | `enumerate_monitors`, `choose_*` |
| **GpuContext** | D3D11 device/context, WinRT interop device, device-lost detection | swap chains, captures | `Renderer::initialize` |
| **CaptureSource** (per display; ref-counted by views) | WGC item/pool/session, latest texture, lifecycle state (starting/live/stalled/closed) | viewport, presentation | `CaptureRunner` capture half |
| **EvidenceSampler** | one global sample per tick → immutable `EvidenceSnapshot` (unfiltered pointer + last-intentional-move time, Win32 caret/focus, UIA worker, pid) | relevance/source filtering | `Win32EvidenceProvider` (remove filter), `UiaEvidenceProvider` (already global) |
| **WorkspaceCoordinator** | workspace config, active-view + boundary state, geometric routing, arbitration, command targeting, rebuild-on-topology/settings | pixels | `render_loop` + globals `main.cpp:66-89` |
| **ViewSession** (per output) | binding (source key, destination key + geometry), `ViewController`, VisualState, OverlayState, OutputSurface (window + swap chain) | evidence sampling, ownership | `ViewController` (already pure and per-view-ready), window creation |
| **ViewRenderer** | reconstruct → colour → overlay passes into an OutputSurface | policy | shader `main.cpp:493-553` |

**Design rules [Rec]:**
- EvidenceSampler is **pull, snapshot-per-tick**, not a pub/sub hub. Routing and arbitration are pure functions that can be unit-tested, in the same style as `view_controller.h`.
- Start with **one frame thread** (sample → coordinate → render all views) and present without holding the context lock across `Present` (use waitable swap chains or frame latency 1). Split into per-output present threads only if the pacing measurement demands it.
- **Topology changes trigger a debounced whole-workspace rebuild** (~0.5–1.5 s settle; a device reset uses the same path). Per-display surgical recovery comes later, if at all.
- **Safety invariant:** never place a full-screen, non-click-through output over the display the user interacts on unless the user explicitly asks. When topology shrinks to one screen, fall back to the windowed view (today's behaviour), never to a full-screen Detail.
- Telemetry gains `view_id`. Diagnostics gain workspace and topology dumps.

**Alternatives rejected:** a separate "ownership subsystem" (over-abstraction); a device per view (option B), which multiplies captures or needs shared-handle/keyed-mutex plumbing for little isolation, since device loss is usually adapter-wide anyway [I]; ZoomText-"Global"-style views whose source moves with activity (confusing, complex).

**Device strategy (Q11):** **Keep A (one shared device) behind an explicit `GpuContext` object that sources and views reference, never a global.** WGC and DXGI handle cross-adapter capture and present through DWM at a copy cost [D/I]. A later split to one device per adapter is contained if hybrid-laptop or USB (IDD) measurements show copy cost matters [U]. Today every captured frame is copied again into `cachedSource_` (`main.cpp:383-390`) [R]; with 3–4 sources on an iGPU laptop that bandwidth needs measuring before any Doxa claim [U].

**Failure modes to design for:** coordinator becoming a god object (keep policy pure and tested); rebuild storms during monitor wake (debounce); a view whose destination disappears (pause and show a hint on a live screen, never remap silently); WGC stalls with no error (per-source frame-age watchdog); device removal (rebuild everything).

## 5. Active-view / crossing policy assessment

| Model | Predictability | Simultaneous motion risk | Context+Detail fit | Shared-source views | Command targeting | Complexity |
|---|---|---|---|---|---|---|
| A. Independent per-view following | Medium: two views can move at once on different evidence (pointer on A, caret on B) | Medium | Fine (one follow view) | Poor: both react | Undefined without an extra concept | Low but hides the needed state |
| B. Single active owner, explicit switch only (ZoomText-like manual) | High | None | Fine | Fine | Natural | Low; poor for keyboard users typing on a non-active screen |
| **C. Single active owner, handed over by activity, routed by geometry, plus explicit switch [Rec]** | High | None | Fine; reduces to today's behaviour | Fine (non-owners `fixed`) | Natural (active view) | Low; a small state machine |

**Recommended semantics (C):** each evidence item routes to the display that contains its anchor, then to the views bound to that source. The **active view** is whichever view's source received the most recent *intentional* activity: pointer movement, or caret/focus change after the last pointer movement. There is also an explicit "switch view" hotkey. Only the active view follows; other views hold. **Overlays render in every view whose viewport contains the target, whether or not that view is following.** Zoom and colour hotkeys target the active view. A small indicator (border or edge tint) shows which view is active.

**Boundary state machine (architecture):** `OnSource(view)` → pointer leaves to a non-source display → `LeftSource(hold)`: no ownership transfer; semantic evidence older than the leave cannot reclaim; *post-leave* caret/focus activity may follow → pointer enters another view's source → hand-off → return → `OnSource`.

**Keep for later UX experiments, not architecture:** Mouse-Buffer-style resistance/dwell (needs a low-level mouse hook or `ClipCursor`, both with side effects), sound cues, linked zoom. **Early experiment worth running:** in Context+Detail, make Detail-only monitors non-enterable by the pointer. The Detail screen has nothing to interact with, and today a pointer that crosses onto it sits at 1x on top of the magnified image [I].

**Evidence that would change this:** formative users preferring independent simultaneous following in Side-by-Side-style work (then allow a per-view `follow: always` override) [U].

## 6. Renderer / text-quality decision

**Implement first (after extraction slice 2):** split the single shader into **reconstruct → colour → overlay** stages, with the view transform explicit. Then ship the winning filter from an **offline filter comparison run now**. Candidates: bilinear (control), Catmull-Rom/Mitchell bicubic, Lanczos-3, sharp-bilinear (integer pre-scale), edge-directed plus adaptive sharpening (e.g., AMD FSR1 EASU/RCAS, MIT licence, provenance recorded). Test on captured frames of Word, Outlook, Excel and Edge at 100% and 150% scaling, zoom 2/3/4/6/8, **ClearType on and off** (sub-pixel colour fringes are magnified too [I]). At most one user control ("Sharp / Smooth").

**Seam to preserve:** a composition stage after reconstruction that can draw layers anchored in source coordinates (overlays today; targeted DirectWrite text over UIA text ranges later). Nothing else.

**Evidence that gates semantic work:** a blinded comparison with low-vision participants or assessors at their working zoom, best raster vs ZoomText xFont. Promote targeted semantic enhancement for one or two apps (Word/Outlook) **only if** best raster is rejected at 2–3x, and only after measuring the per-app compatibility cost. The matched 2x ZoomText benchmark should run *after* the filter is chosen, not against bilinear. **Answer to Q16: yes, staged is justified; modify step 1 as above.** Q17: the filter comparison and ClearType check can run before, or in parallel with, extraction. GPU cost at 4K, high-refresh behaviour and the matched ZoomText benchmark come after extraction. None of these blocks the architecture.

## 8. 2–4 monitor configuration model

**Identity (Q13) [Rec]:** fingerprint = EDID manufacturer + product + serial + friendly name (from `DisplayConfigGetDeviceInfo` target name) + monitor device path (encodes connector/port) + last geometry, DPI and resolution. Adapter LUIDs change between boots, so they are not persistent identity [D]. GDI names (`\\.\DISPLAYn`, today's key) are not stable [R/D]. Matching order: exact fingerprint → EDID + path → EDID + relative position → position only (low confidence). **If confidence is low or a role would move onto a different physical screen, do not guess.** Apply a safe default, show a large "Screens changed — confirm" prompt on the screen with the pointer, and offer an "Identify screens" overlay. Identical panels with serial 0 can only be told apart by port or position, so verify on real panels [U].

**Minimum schema v2 (Q14):**
```
schema_version: 2
displays[]:  { key, fingerprint{…}, last_rect, last_dpi }
layouts[]:   { signature = sorted set of display keys (+ arrangement), workspace_id }   # docked vs undocked recall
workspaces[]: { id, name,
  views[]: { id, source:{display_key}, destination:{display_key, geometry:"full"},
             zoom, visual{mode,brightness,contrast,tint}, follow{pointer,caret,focus},
             overlays{pointer,caret,focus: preset_id}, locator_on_source: bool },
  active_view_policy: { mode:"activity_handoff", boundary:{hold_on_leave:true} } }
global: { hotkeys, language, assistance, update }
```
Reference = a display bound to no view (implicit). Context+Detail = `{source A → dest B}`. Self-magnify = `{A → A}`. Clone/presentation = two views of one source with different visual state, so **no special cases** are needed. Span cannot be expressed, by design. **Rule:** reserve *structure* now (lists, identity records, geometry object). Add *fields* only when the feature is built; optional fields are non-breaking under `schema_version`. Format: keep INI with per-view sections, or JSON through a vendored MIT library with provenance. Either works; migration and versioning are what matter.

## 9. Compatibility / supportability plan

- **Tier 1 (must pass every release):** Word, Excel, classic and new Outlook, Edge, Chrome, new Teams (WebView2), File Explorer, Start/Search, Settings, Notepad, Windows Terminal, one PDF viewer. **Tier 2:** Firefox, VS Code (Electron), Zoom/Slack, Java/Swing, LibreOffice. **Explicitly unsupported initially:** Citrix/RDP-published apps, secure desktop/UAC (fall back to Windows Magnifier), elevated apps' semantic evidence (UIPI) [D/I], protected video.
- **Per app/test:** evidence presence by source (UIA TextPattern2 / selection / Win32 caret / focus), caret and focus rect error vs harness ground truth, follow correctness, overlay placement, one text-quality still.
- **Environment axes:** DPI 100/150/200 and mixed; left/right/above layouts with negative coordinates; 60/144 Hz; HDR on/off [U: WGC 8-bit on HDR desktops]; sleep/wake; dock.
- **Regression:** extend the existing deterministic harness into per-app fixture scripts. Results go to a versioned **compatibility ledger** (app version + Windows build + pass/fail), run nightly on the Dell.
- **Diagnostics additions:** evidence availability for recent foreground apps; topology/fingerprint history; workspace dump; lifecycle events (stalls, rebuilds, device loss); one-click content-free support bundle (consistent with the current privacy stance [R]). Note: capture-excluded windows are also invisible to screen sharing and remote support [D]. That is good for share-safety but means supporters cannot see overlays.
- **Before claiming "workplace useful":** Tier 1 passes on two Windows builds and three DPI settings, and the slice 6 lifecycle tests pass.
