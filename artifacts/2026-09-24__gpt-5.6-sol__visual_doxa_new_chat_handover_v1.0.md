# 2. Product framing

## 2.1 Primary product

The primary product is **Doxa as a useful low-vision workstation**.

Visual is the Windows magnification/tracking software companion and the current engineering test bed. It should not drift into a generic magnifier feature race merely because competitor products contain many features.

The product thesis to test is:

> Doxa + Visual can combine strong magnification with spatially persistent information so that people with low vision can work with more context and less navigation cost, while keeping the physical workspace comfortable and configurable to individual needs.

This is a research hypothesis, not yet a marketing claim.

## 2.2 Current Doxa research model

Evaluate Doxa configurations across three coupled dimensions:

1. **Magnification / visual access** — readable detail, target acquisition, orientation, pointer/caret/focus recovery.
2. **Productivity / information exposure** — less panning and window switching, easier comparison/reference, fewer errors, faster task completion.
3. **Ergonomics / visual load** — head/gaze movement, fatigue, clutter, distraction, posture, viewing distance.

Personal preference, functional vision, habitual magnification strategy and task type moderate the optimum.

The central experimental question is:

> Does additional persistent screen space reduce viewport-navigation cost faster than it increases physical visual-navigation cost?

## 2.3 Critical research guardrail

**Do not assume more screens are automatically better.**

When Doxa arrives, screen count is an experimental variable: test 1, 2, 3 and 4 active screens. Test laptop-close Detail versus upper-centre Detail. Test stable versus automatically changing secondary surfaces. Do not hard-code permanent semantic roles before evidence supports them.

## 2.4 Scope until Doxa hardware arrives

Until the Doxa hardware is physically available:

- keep Visual focused on the current two-monitor magnification/tracking POC;
- make visible behavior deterministic and measurable;
- strengthen automated visual regression;
- validate representative application families;
- prove installer/update/support plumbing without allowing it to displace the core magnification work;
- do not build speculative four-screen runtime logic merely because Doxa will eventually have more displays.

# 4. Current Visual architecture

Current production flow is effectively:

**WGC source capture -> Windows POI evidence -> POI arbitration -> viewport controller -> locator model -> D3D11 crop/scale/locator -> non-activating Detail window on another display**

Key design separation:

- graphics pipeline: capture -> cached GPU texture -> crop/scale/image processing -> presentation;
- intent pipeline: pointer/caret/focus evidence -> POI arbitration -> viewport state -> locator state.

Do not bury intent policy in capture callbacks.

## 4.1 Important cadence correction already implemented

The original integrated alpha rendered/tracked only when Windows Graphics Capture emitted `FrameArrived`. This was wrong because cursor capture is disabled and hardware-pointer motion on otherwise static pixels does not guarantee fresh WGC frames.

The implementation was refactored so:

- WGC callback caches the latest source texture;
- an independent ~60 Hz interaction/render loop samples pointer/UIA/Win32 evidence, arbitrates POI, updates viewport and renders from the cached texture;
- D3D11 immediate-context access is serialized.

See:

`artifacts/2026-09-23__gpt-5.6-sol__interaction_cadence_fix_and_browser_compatibility_v0.1.md`

# 9. Automated pointer-visibility run: evidence and caveats

Run folder:

`lab/benchmarks/visual_regression/runs/2026-09-24_08-03-26__pointer_visibility/`

Tested executable:

`app/build/Release/visual_app.exe`

Version resource:

`0.1.0-alpha.1`

Recorded:

- 3840x1080 recording surface;
- 1,080 Visual telemetry frames;
- 561 independent cursor-ground-truth samples;
- zero Present failures.

Telemetry phase summary:

- slow horizontal: pointer selected 98.4%; 2 >100 ms pointer-age frames; max ~897 ms;
- fast horizontal bursts: pointer selected 100%; max pointer age ~44.7 ms;
- fast zigzag: pointer selected 100%; max pointer age ~21.9 ms;
- edge teleports: pointer selected 98.6%; one >100 ms pointer-age frame; max ~128 ms;
- telemetry reported locator visible throughout these phases.

## 9.1 Pixel-analysis result that must be interpreted carefully

A coarse 8 fps local expected-position detector initially flagged apparent missing locator samples.

A later global search showed all fast-horizontal suspect frames had the crosshair **elsewhere** on the destination rather than truly absent. For that subset:

- suspect frames: 13;
- crosshair found elsewhere: 13;
- true absent: 0.

This is evidence of **position/trailing/mapping mismatch**, not renderer omission, for those fast-horizontal samples.

A later full-screen scan of seven suspect samples during/around fast zigzag found:

- crosshair found somewhere: 5;
- crosshair not detected anywhere: 2;
- coarse longest apparent absence: 2 samples / ~250 ms at 8 fps.

Those two samples are **not yet a confirmed rendering defect**. Native 30-fps forensic confirmation was started but not completed before this handover. Possible explanations include:

- true brief locator omission;
- detector false negative;
- video/telemetry synchronization error;
- locator geometry changing outside the detector assumptions;
- DPI/coordinate error in the harness.

Do not patch the renderer solely on the coarse 250 ms result.

## 9.2 Important instrumentation flaw discovered

The first pointer-visibility harness used WinForms display coordinates before setting per-monitor DPI awareness. On the 150%-scaled primary display it therefore saw a **1280x720 logical primary** while the physical desktop is 1920x1080.

This is the same class of 1.5x DPI virtualization problem already found in an earlier pointer-stress harness.

The newer pointer-crossing harness explicitly calls PMv2 (`SetProcessDpiAwarenessContext(-4)`) before enumerating displays and sees both physical screens as 1920x1080.

**Action:** make `run-pointer-visibility.ps1` PMv2-aware, add explicit video/telemetry sync markers, then rerun before treating its spatial pixel findings as canonical.

# 10. Pointer-crossing hypothesis and dedicated run

During the user's manual test, the user later suggested a simpler explanation: under fast motion, the native Windows mouse pointer may have crossed onto the secondary Detail screen while the user was searching for it on the main screen.

A dedicated run was created to test this objectively.

Run folder:

`lab/benchmarks/visual_regression/runs/2026-09-24_08-54-31__pointer_crossing/`

Physical topology in the PMv2-aware test:

- primary/source: `DISPLAY1`, 0..1919 x 0..1079, 1920x1080;
- secondary: `DISPLAY2`, 1920..3839 x 0..1079, 1920x1080.

Independent `GetCursorPos` ground truth recorded 659 samples.

Objective monitor-membership result:

- `primary_center_hold`: 75/75 on primary;
- `primary_edge_hold`: 75/75 on primary;
- `cross_to_secondary`: 8 primary + 33 secondary;
- `secondary_near_hold`: 90/90 on secondary;
- `secondary_sweep`: 76/76 on secondary;
- `secondary_far_hold`: 90/90 on secondary;
- `return_to_primary`: 40 secondary + 21 primary;
- `primary_return_hold`: 90/90 on primary.

Therefore the hypothesis that the physical pointer can leave the main/source screen and remain on the Detail screen is **objectively supported**.

This makes the user's original manual “lost pointer” report plausibly explainable by monitor crossing. It does **not** prove every perceived disappearance has that cause.

## 10.1 Remaining issues in this crossing run

The run recorded `desktop.mp4`, but `visual_telemetry.csv` is zero bytes. The harness logged that a Visual process was started, but it did not verify the process remained alive and emitting telemetry.

The delegated video-analysis task was cancelled before completing. Therefore still determine:

- whether the native pointer is visibly present on the secondary during the long holds in `desktop.mp4`;
- whether an existing Visual instance, immediate Visual exit, command-line/logging issue, or another lifecycle condition caused the empty telemetry file;
- how Visual itself behaves when the native pointer is outside the source display.

The ground-truth crossing result remains valid independently of the empty telemetry file.

# 11. Product-design question exposed by pointer crossing

For a dedicated Detail/output surface, decide deliberately what should happen when the native pointer reaches that monitor boundary.

Options to experiment with, not yet product decisions:

1. **Normal Windows crossing** — current ordinary extended-desktop behavior.
2. **Ignore pointer POI outside the source display** — allow crossing, but do not have Visual treat coordinates on its own Detail surface as a source target.
3. **Optional confinement to source display while tracking is active** — potentially useful but restrictive and may interfere with legitimate multi-monitor work.
4. **Strong monitor-membership feedback / pointer finding** — make it obvious which screen owns the real pointer.

Do not implement `ClipCursor` or another confinement policy simply because the manual report occurred. First finish the crossing behavior evidence and decide the expected UX.

This question is directly relevant to Doxa, where some displays may become output/context surfaces rather than ordinary interactive desktops.

# 20. Evidence hierarchy and engineering philosophy

Continue using:

**research -> hypothesis -> experiment -> evidence -> architecture decision -> production implementation**

For every material statement, distinguish:

- observed repository fact;
- named test result;
- documented external fact;
- hypothesis;
- recommendation.

Do not call internal timestamps photon latency. Do not call telemetry evidence equivalent to visible pixel evidence. Do not convert a coarse detector result into a renderer bug without frame confirmation.

Prefer simple Windows-native mechanisms. Preserve a clean graphics/intent separation. Avoid speculative abstractions.

Competitor research remains clean-room only: public documentation, ordinary observed behavior, and properly licensed open-source material. Never obtain or incorporate proprietary competitor source/assets/confidential internals.

# 23. Final handover summary

Visual has crossed an important threshold: it is no longer just a rendering spike. It is a functional two-monitor alpha with a real public distribution pipeline, structured diagnostics, deterministic interaction telemetry and now the beginnings of pixel-grounded visual regression.

The most important lesson from this conversation is that **internal telemetry is not enough** for graphics/accessibility behavior. The project should retain synchronized video/pixel evidence as a first-class regression signal.

The immediate technical risk is not lack of features. It is incorrectly interpreting pointer/locator behavior because of monitor crossing, DPI virtualization or imprecise video synchronization. Close that evidence loop first.

The immediate distribution risk is not package creation: GitHub + Velopack release publication works. The remaining issue is correct app lifecycle/update integration and proving install/update/uninstall behavior on a real Windows profile.

The long-term product risk is prematurely assuming that Doxa should always use all four screens. Keep screen count, display roles, viewing distance and stability/dynamism as experimental variables until low-vision task evidence supports defaults.
