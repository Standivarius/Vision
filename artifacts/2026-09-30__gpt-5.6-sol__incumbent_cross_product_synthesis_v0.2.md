# ZoomText + SuperNova cross-product synthesis for Vision v0.2

**Date:** 2026-09-30  
**Status:** pre-Opus product/architecture synthesis  
**Inputs:** current Vision baseline; ZoomText comprehensive assessment v0.2; SuperNova comprehensive assessment v0.1; manual-derived feature inventory; earlier hands-on benchmark evidence.

## 1. Purpose

The incumbent research should not be handed to Opus as two feature catalogues. The useful output is a set of recurring **user problems and architectural primitives**.

ZoomText and SuperNova often solve the same problem with different product metaphors. That difference is especially useful because it exposes where Vision needs an architectural seam rather than a copied feature.

## 2. The recurring problem families

| User problem | ZoomText pattern | SuperNova pattern | Current Vision | Product/architecture conclusion |
|---|---|---|---|---|
| Make content large enough without losing control | Full/Overlay/Lens/Line/Docked; many zoom steps | Full/Fixed/Glass/Resizing/Split; many zoom steps | Full-screen Detail; 1x–4x; single-monitor fallback | **Core magnification quality; do not chase geometry parity** |
| Keep the active thing visible | Pointer/caret/focus tracking, alignment and panning | Pointer/caret/focus following, smooth movement | Pointer/Win32/UIA evidence + arbitration + viewport controller | **Core; compatibility quality is a moat** |
| Know where the pointer/caret/focus is | Pointer/caret/focus enhancement schemes | Highlighting presets, pointer schemes | Basic locators/highlights | **Core orientation layer; small strong preset set** |
| Recover global context | 1x toggle, View Locator, Zoom with 1x | Overview Mode, split/glass views, Margin Release | Exact temporary 1x/return + Context locator | **Core; Vision already has a strong base** |
| Reduce glare / improve visual discrimination | Colour filters, Smart Invert, brightness/contrast | Colour schemes, brightness/contrast/tint, Colour Replace | Contrast/invert/grayscale | **Core subset; modest expansion** |

## 3. Important differences that Opus should challenge

### 3.1 Multi-monitor ownership

This is the strongest architecture disagreement exposed by the incumbents.

**ZoomText:** several MultiView outputs can exist, but documented behaviour centres on one active moving view at a time, with automatic hand-off and explicit Active View switching.

**SuperNova:** Side-by-Side is presented as independent applications/views with their own magnification, colour and tracking behaviour, plus Mouse Buffer and monitor switching.

**Current Vision proposal:** shared EvidenceHub plus multiple ViewSessions, each capable of filtering global evidence and applying its own follow policy.

None should be assumed correct. Opus should compare:

1. independent view sessions;
2. one active semantic-follow owner with inactive/stable views;
3. hybrid ownership based on source/destination roles or user activity.

The failure mode to avoid is several magnified views moving simultaneously in ways the user did not intend.

### 3.2 Context recovery versus context relocation

Both incumbents show that “orientation” is larger than temporary 1x.

There are at least four strategies:

1. **zoom out / return** — Vision temporary 1x;
2. **show where the viewport is** — Vision locator / ZoomText View Locator / SuperNova Overview;
3. **pin remote content** — Freeze View / Hooked Areas;
4. **move relevant remote context near attention** — ZoomText Tethered View.

Vision should model these as one context-management problem family. It does not need all four in version one, but architecture should not make 3–4 expensive later.

### 3.3 Text quality

The incumbent evidence argues against a binary choice between “raster is enough” and “build xFont/True Font”.

Both mature products expose fallback behaviour. ZoomText explicitly has xFont plus geometric smoothing and application exclusions; Live Text View is another fallback. SuperNova also treats text quality as a dedicated subsystem.

The safer architectural principle is:

- robust raster baseline;
- rendering-enhancement seam;
- targeted semantic text enhancement only if evidence justifies it;
- optional clean-text/read view as another tool, not a universal renderer replacement.

The Word comparison is now sufficient to narrow the architecture question: ZoomText xFont was judged smooth and natural at 2x; at 4x it remained crisp but showed local glyph-shape distortions, while current Vision remained geometrically stable but visibly softer. This supports improving raster/GPU reconstruction first, with targeted semantic enhancement kept as an optional seam rather than a universal renderer.

## 4. Candidate Vision feature set

### 4.1 First-product core

The combined research supports a deliberately narrow first product:

1. **High-quality magnification**
   - practical fractional zoom range;
   - full-screen/detail workflow;
   - smooth, predictable viewport movement.

2. **Tracking quality**
   - pointer;
   - text caret;
   - keyboard focus;
   - compatibility work across Office, browsers and common Windows UI frameworks.

3. **Orientation layer**
   - exact temporary 1x/return;
   - viewport locator/overview;
   - small, strong pointer/caret/focus cue presets;
   - clear monitor-boundary feedback.

4. **Visual enhancement**
   - colour/contrast/invert;
   - brightness/contrast/tint;
   - a small preset set rather than incumbent-scale catalogues.

5. **Generic 2–4 monitor model**
   - per-view zoom and visual state;
   - explicit view ownership/follow policy;
   - same-monitor and cross-monitor source/destination bindings;
   - deliberate monitor-crossing policy;
   - stable topology/monitor identity recovery.

6. **Text-quality architecture**
   - good raster baseline;
   - a renderer seam that allows better smoothing/sharpening or targeted semantic enhancement later;
   - no premature commitment to full xFont/True Font parity.

7. **Product quality**
   - persistence;
   - install/update;
   - diagnostics;
   - bounded compatibility promise;
   - contextual help/discoverability.

### 4.2 Preserve architectural seams, but do not promise at launch

- one useful single-monitor lens/docked/contextual geometry;
- pinned reference/context regions;
- Tethered-like dynamic context relocation;
- app-specific settings;
- clone/standard-view collaboration;
- presentation mode;
- clean-text / simplified reading view;
- non-visual boundary cues.

### 4.3 Defer unless later evidence promotes them

- Span across monitors;
- dozens of pointer/caret/focus styles;
- full custom highlight editors;
- full profile/situation-setting complexity;
- Doc Reader/AppReader/Line View as major product pillars;
- screen-reader/Braille stack;
- OCR/Finder;
- camera/whiteboard;
- touch;
- Secure Mode / logon accessibility;
- broad Citrix/RDP/virtual-environment promise.

## 5. What should not be inferred from incumbent breadth

Three traps are now clearer.

### Trap A — feature count as product maturity

Many incumbent capabilities are accumulated specialist options. Their presence proves a user problem exists somewhere, not that Vision needs the same control.

### Trap B — common feature means mandatory launch feature

A feature appearing in both products may simply be a mature-market expectation for some segment. Value, implementation cost and support burden still matter.

### Trap C — Vision’s multi-monitor idea automatically differentiates

Both incumbents already have significant multi-monitor functionality. Vision differentiation cannot simply be “works with several screens”.

A more credible differentiation hypothesis is:

**simpler, more predictable multi-monitor low-vision work with strong orientation and context management, without incumbent-scale configuration complexity.**

That hypothesis still requires user/dealer validation.

## 6. Architecture questions for Opus

The independent review should answer or challenge:

1. Is the proposed MonitorRegistry + CaptureSource + shared EvidenceHub + ViewSession decomposition the right abstraction?
2. Should following ownership be per-view, single-active-view, or hybrid?
3. Should per-view visual enhancement and overlay policy live inside ViewSession or in separate policy objects?
4. How should same-monitor magnification avoid recursion and remain composable with cross-monitor views?
5. What monitor-boundary state machine is simplest and least surprising?
6. Does the renderer need an explicit text-quality extension seam now?
7. Does context pinning/relocation require a generic sub-view model now, or can it be added later safely?
8. Which first-product features materially affect the architecture and therefore must be decided before refactoring?
9. Which attractive incumbent features should be explicitly excluded so they do not contaminate the first architecture?

## 7. Evidence boundaries carried into Opus

The package should not imply more evidence than exists.

- ZoomText MultiView hand-off semantics are current vendor-documented and installed-state supported, but not cleanly behaviourally exercised in the final evaluation session.
- ZoomText Tethered View integrations are installed-state verified but not real-task validated.
- ZoomText Live Text View is installed/configured but not hands-on validated.
- ZoomText xFont was visually assessed in Word: strong/smooth at 2x and crisper than Vision at 4x, but with local glyph-shape distortion at 4x. Phone-photo evidence supports the direction but is not a pixel-accurate benchmark. A matched 2x Vision-vs-ZoomText comparison remains useful as a later release-quality check.
- SuperNova Mouse Buffer, some custom highlighting details, and Hooked-Area subjective task value remain documented/installed rather than fully behaviourally validated.
- These uncertainties should be visible to Opus, not filled with assumptions.

## 8. Bottom line

The combined incumbent research supports a **small surface, deep quality** strategy, but the “small surface” is broader than magnification + tracking.

The smallest defensible Vision product appears to require:

- magnification quality;
- tracking quality;
- orientation cues;
- context recovery;
- colour/contrast;
- explicit multi-monitor ownership/boundary behaviour;
- renderer-quality extensibility;
- compatibility/supportability.

Pinned/tethered context, app-specific settings and collaboration are credible next-layer features. Reading ecosystems, screen-reader breadth, camera/touch and incumbent-scale configurability should stay outside the first product unless new user evidence changes the boundary.
