## User-provided leads

The Doxa hardware is described as involving USB-C power/data, HDMI, possible audio I/O and likely Silicon Motion display technology. These are leads for investigation, not verified repository facts.

## Public Silicon Motion evidence

Silicon Motion currently markets USB Display Interface SoCs for universal docking/display products.

Public product material states:

- SM770 can support up to three concurrent 4K UHD 3840x2160@60 displays;
- Silicon Motion uses CAT (Content Adaptive Technology) to compress display data and reduce host bandwidth/CPU load;
- InstantView software is intended to provide plug/display workflows and can update host software and device firmware;
- Silicon Motion publishes separate Windows driver/MSI downloads for SM76x and SM77x families.

Current public download pages observed on 2026-09-20:

- SM76x Windows 11/10 driver/MSI: V2.24 R01, released 2025-09-03;
- SM77x Windows 11/10 driver/MSI: V4.7 R06, released 2026-06-22.

Sources:

- https://www.siliconmotion.com/products/USB-Display-Docking-SoC/detail
- https://www.siliconmotion.com/product/Graphics-Display-SoCs.html
- https://www.siliconmotion.com/downloads/
- https://www.siliconmotion.com/downloads/SM770-drivers.html
- https://www.siliconmotion.com/events/instantview/

These public facts do **not** establish which controller Doxa uses. The same vendor supports multiple controller families and deployment models.

## Windows driver deployment evidence

Microsoft documentation recommends Windows Update as the preferred public distribution channel for driver packages because it provides signing, security checks, controlled rollout and global delivery infrastructure.

Windows stages installable driver packages into the Driver Store. SetupAPI device-install logs (`%SystemRoot%\inf\SetupAPI.dev.log`) are a primary diagnostic source for driver installation and selection behavior.

Public Windows references:

- https://learn.microsoft.com/en-us/windows-hardware/drivers/develop/distributing-a-driver-package
- https://learn.microsoft.com/en-us/windows-hardware/drivers/dashboard/publish-a-driver-to-windows-update
- https://learn.microsoft.com/en-us/windows-hardware/drivers/install/driver-store
- https://learn.microsoft.com/en-us/windows-hardware/drivers/install/setupapi-text-logs
- https://learn.microsoft.com/en-us/windows-hardware/drivers/install/whql-release-signature
- https://learn.microsoft.com/en-us/windows-hardware/drivers/install/signature-categories-and-driver-installation

Production Doxa support should therefore prefer signed, vendor-supported packages and avoid relying on unsigned/test-signed field installation.

## Main conclusion

Do not design the production Doxa installer around a guessed controller or guessed vendor package.

First establish the exact hardware stack from:

1. manufacturer BOM/specification;
2. Windows USB/PnP hardware IDs on a real connected unit;
3. installed/supported driver package metadata;
4. firmware version/update/recovery information;
5. redistribution/update-channel rights.

Then choose the deployment path.

## Factory versus PC responsibilities

The hardware factory can normally control:

- device firmware;
- EEPROM/configuration;
- USB descriptors/VID/PID/serial behavior;
- EDID/device configuration;
- factory test/calibration data;
- onboard storage/software content if such storage is part of the design.

The factory normally cannot preinstall software into an arbitrary customer's future Windows laptop. Host software needs an explicit distribution mechanism such as Windows Update, a Doxa setup/bootstrapper, enterprise MSI, or a vendor technology such as an InstantView-style host workflow.

The exact Doxa production process therefore requires both a factory-flash specification and a Windows host-software distribution specification.

## Installer/support recommendation

Build a deterministic Doxa setup/diagnostics layer that can:

- identify hardware revision and connected functions;
- inspect approved driver/firmware versions;
- install/repair approved signed packages;
- collect Windows/PnP/SetupAPI/display/USB diagnostics;
- run known health checks;
- execute bounded recovery actions;
- produce a support bundle.

An optional cloud LLM can reason over structured diagnostics and propose one of the bounded actions with user approval. It should not receive unrestricted administrator shell authority and should not be required for normal installation.

## What can be learned once Doxa is connected

A read-only first pass on the development PC should be able to establish much of the real architecture without opening the hardware:

- USB VID/PID/interface tree;
- composite/hub topology;
- display adapter and monitor identities;
- installed INF/provider/version/signature;
- service/process names;
- current firmware/version strings if exposed;
- audio/network endpoints;
- Windows problem codes;
- install history from SetupAPI logs;
- monitor topology/adapter mapping;
- hot-plug/sleep/reconnect behavior;
- likely controller family from authoritative device/package identifiers.

If photographs/board markings and manufacturer information are also available, confidence increases significantly.

## What should still come from the manufacturer

Do not try to infer or reverse-engineer when the OEM can provide authoritative information about:

- exact BOM;
- internal firmware protocol/source;
- factory programming values;
- power-delivery limits;
- electrical constraints;
- proprietary compression implementation;
- redistribution/licensing rights;
- golden/recovery firmware;
- hidden engineering diagnostics;
- official compatibility and escalation policy.
