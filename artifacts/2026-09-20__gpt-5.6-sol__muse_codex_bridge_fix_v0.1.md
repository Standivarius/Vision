# Muse through Codex CLI — Visual bridge fix v0.1

**Date:** 2026-09-20  
**Project:** Visual  
**Status:** Muse profile and normal bridged execution verified; timeout semantics implemented; exact post-final lingering-process race not reproduced on the current Visual Codex build.

## Basis

The handoff was based on the File Library report:

`2026-09-20__aigov_assistant__muse_codex_cli_handoff_fix_report_v0.1.md`

That report established an important semantic rule: a Codex watchdog timeout must not turn a completed model answer into a failed model task merely because the outer Codex process has not exited yet. If a non-empty `last_message.txt` exists at watchdog time, semantic state should be completed while `timed_out=true` remains visible. If there is no final answer, the timeout remains a failure.

The Visual bridge was architecturally different from the source report: Codex was detected but still marked `execution_status: not_wired`, so Visual required a real Codex worker rather than only the narrow timeout-branch correction.

An unrelated MCP OAuth error was emitted on stderr but did not affect Muse execution or the final answer. No credential was requested, printed or modified.

## Visual bridge implementation

`bridge/server.mjs` now:

- wires the `codex` provider for real execution;
- exposes `muse-spark-1.3-contributor` as a supported Codex model;
- maps it to Codex profile `muse-spark-1-3-contributor`;
- keeps delegated Codex execution read-only only;
- executes in the existing disposable Visual snapshot used for delegated read-only work;
- captures Codex `--output-last-message` into `last_message.txt`;
- transports multiline task prompts through stdin on Windows;
- records semantic `result` / `error` separately from process diagnostics;
- preserves `timed_out`, `timeout_seconds`, `final_message_status`, `exit_code`, and `process_exit_code`;
- treats watchdog timeout + captured final message as semantic completion;
- treats watchdog timeout + no final message as failure;
- keeps ordinary non-timeout non-zero Codex exit as failure.

`bridge/openapi_chatgpt_compact.json` now documents Muse as a supported Codex model.

## Verification

### Normal bridged Muse canary

Task:

`Return exactly MUSE_BRIDGE_OK and nothing else.`

Observed through `startReadOnlyLocalAgentTask` / `getLocalAgentTask`:

- status: `completed`;
- result: `MUSE_BRIDGE_OK`;
- error: `null`;
- `timed_out=false`;
- `final_message_status=captured`;
- `exit_code=0`;
- `process_exit_code=0`;
- duration: ~11 s including wrapper/snapshot overhead.

### Current true-timeout behavior

A 5-second Muse watchdog produced no final message before expiry.

Observed:

- status: `failed`;
- `timed_out=true`;
- `final_message_status=missing`;
- timeout result preserved;
- process was terminated.

This verifies that a real no-answer timeout still fails.

### Narrow handoff-race reproduction

A 6-second and 7-second watchdog both completed normally before the watchdog, while 5 seconds expired before a final message existed. Therefore the current Codex build did not naturally reproduce the narrow state where `last_message.txt` is complete but the outer process remains alive past the watchdog.

The semantic branch for that state is implemented directly from the handoff requirement, but it should not be claimed as live-race verified on Visual until such a run occurs naturally or a dedicated deterministic process-hold test is added.

## Current operating rule

Muse is now available for bounded read-only delegated work through the ordinary local-agent API using:

- provider: `codex`
- model: `muse-spark-1.3-contributor`

Writable Muse/Codex delegation remains intentionally disabled until path-scoped write enforcement is implemented.
