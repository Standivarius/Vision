# ZoomText Magnifier comprehensive assessment v0.3

**Date:** 2026-09-30
**Status:** Comprehensive ZoomText assessment complete for Vision pre-Opus product/architecture review
**Hands-on build previously tested:** ZoomText 2026.2606.73.400
**Current vendor release consulted:** ZoomText 2026.2608.15.400

## Purpose

This assessment corrects the earlier ZoomText research, which concentrated too heavily on pointer, caret, focus, zoom and monitor crossing.

The objective is not feature parity. It is to determine which ZoomText capabilities solve important low-vision problems, which could materially affect Vision architecture or first-product scope, and which should be deferred or excluded.

## Evidence model

Conclusions distinguish:
- **Hands-on verified** — directly exercised in the earlier Dell ZoomText session.
- **Current manual/vendor documented** — supported by the current ZoomText 2026 guide or current Freedom Scientific release material.
- **Architecture inference** — implication for Vision, not an incumbent implementation claim.
- **Open hands-on gate** — behaviour important enough to justify a focused reinstall test.

The previous ZoomText session used official build 2026.2606.73.400 in the documented 40-minute evaluation mode after the required reboot. Current 2026.2608.15.400 release notes are also used for up-to-date product/support context.

## High-level product model

ZoomText Magnifier is better understood as six interacting layers rather than “magnification plus tracking”:

1. **Magnification / window geometry** — Full, Overlay, Lens, Line, Docked, multi-monitor view modes and 1x recovery.
2. **Rendering quality** — xFont, Bold xFont, geometric smoothing and Live Text View fallback.
3. **Navigation / orientation** — tracking, alignment, smooth panning, View Locator, border cues, pointer routing and constraints.
4. **Context relocation / persistence** — Tethered View, Freeze View and application-specific configurations.
5. **Visual enhancement** — colour, Smart Invert, pointer/caret/focus enhancement schemes and per-monitor enhancement assignment.
6. **Support / deployment / adoption** — secure mode, diagnostics, screen-sharing policy, command infrastructure and application settings.

For Vision, the important lesson is not to reproduce all six surfaces. It is to recognise which underlying problems recur across both ZoomText and SuperNova and design the smallest reusable primitives.

## Human visual xFont check — Word

User observation on Dell, comparing ZoomText xFont behaviour in Microsoft Word:
- At **2x**, text looked **quite good, smooth and natural**.
- At **4x**, glyph edges remained smooth, but the **letterforms themselves showed small local shape distortions / bulges** (described by the user as little “pregnant” deformities).

Interpretation: xFont provides a meaningful text-quality advantage at moderate magnification, but higher magnification still exposes shape artefacts. This supports keeping a higher-quality text-rendering seam in Vision, while arguing against making the entire renderer depend on a universal semantic/xFont-like path. A layered design remains the stronger hypothesis: raster/WGC baseline, high-quality geometric/shader path, targeted semantic text enhancement where reliable, and optional clean-text/Live-Text-style fallback.


## 2026-09-30 matched 4x visual comparison evidence

User supplied phone photos of ZoomText at 4x in Microsoft Word after previously observing ZoomText directly at 2x and 4x.

Observed/confirmed:
- ZoomText 2x was judged smooth, natural and visually strong.
- ZoomText 4x retained smooth edges but showed local glyph-shape bulges/deformations.
- In the 4x phone photos, ZoomText body text appears crisper than the current Vision 4x raster view, but the photos also show shape irregularity consistent with the user's direct observation.
- The current Vision 4x screenshot preserves overall glyph geometry comparatively well but is visibly softer/blurrier.

Evidence boundary:
- Phone photos are affected by camera sharpening, perspective, moire and display-pixel interaction, so they are not a pixel-accurate renderer benchmark.
- The user's direct visual judgement is therefore stronger evidence than the photograph for ZoomText's 4x deformation behaviour.

Architecture implication:
- Vision should target at least ZoomText-class perceived text quality around 2x-3x.
- At 4x+, Vision should improve crispness while preserving glyph geometry better than the current raster path.
- This supports a layered renderer strategy rather than a wholesale xFont clone.

## Remaining feature families

The manual-derived sweep also covers the following areas that were missing from the earlier partial matrix:

- **Caret enhancement:** configurable caret visibility/locator treatment. Vision should keep a small preset set and separate visibility from following.
- **Focus enhancement:** explicit focus locator/highlight treatment. This is first-product orientation infrastructure, not cosmetic polish.
- **Tracking breadth:** pointer, caret, focus, controls, menus, tooltips, windows and alerts. Vision should not copy every trigger, but compatibility work across common Windows/Office/browser surfaces remains core.
- **Alignment and viewport policy:** edge, centre and smart alignment plus smooth panning. These confirm that viewport motion policy is itself a product subsystem.
- **Pointer routing and constraints:** route pointer into view/to focus and constrain travel. Useful optional aids, but potentially intrusive and therefore not default-table-stakes.
- **Configuration/Application Settings:** global configuration plus per-application overrides. Vision should preserve schema seams for app-scoped state even if the first UI remains simple.
- **Screen sharing:** unenhanced sharing by default with an option to share the magnified result. Useful workplace behaviour, but phase 2 rather than a launch blocker.
- **Secure/logon/shared-computer modes:** enterprise/deployment completeness, not first-product core.
- **Three-display support:** direct evidence that mature magnifier workflows extend beyond two screens; supports Vision's 2-4 monitor proposition.
- **Finder/OCR/Camera/Touch/Reader:** useful incumbent breadth, but outside the focused first-product boundary unless later user evidence promotes them.
- **Diagnostics/support tooling:** essential commercial infrastructure. A focused assistive product still needs strong compatibility reporting and recovery.
- **Layered hotkeys, Quick Access and contextual help:** adoption/discoverability features worth adapting in a simpler form.

## MultiView conclusion

Current ZoomText documentation establishes two distinct multi-monitor policies:

- **MultiView Local:** each view is constrained to its own desktop;
- **MultiView Global:** each view can track across all desktops.

Only one view is active/moving at a time. The active view can change when activity crosses desktops and can be switched explicitly. Views can retain independent magnification, with optional linked zoom. Boundary markers, sound cues and pointer resistance make monitor crossing an explicit interaction problem.

For Vision, this is important evidence against assuming that every view should independently follow one shared EvidenceHub at all times. Opus should compare at least two policies:

1. independently active per-view following; and
2. explicit/transferable active-view ownership.

The architecture should support either policy without coupling it to capture or rendering.

## Tethered View / context-relocation conclusion

ZoomText's Tethered View is conceptually different from Freeze View or a static Reference monitor. It brings remote-but-relevant information close to the user's current locus and allows interaction with that content. Installed configuration on the Dell includes Windows Start search, Excel Formula Bar and Word Comments scenarios.

This suggests a distinct **context-relocation** primitive:

- a region is selected because of task context;
- it is presented near the current work location;
- it may update dynamically;
- it is not simply a frozen screenshot.

Vision should not implement Tethered View before the multi-view core is stable, but the source/view model should not make this impossible. A future pinned/reference/context view should be able to bind to either a physical source region or a semantic/task-derived region.

## Live Text View conclusion

Live Text View is not a replacement for the main magnifier. It is a separate clean-text presentation path intended especially for applications where xFont smoothing is unavailable. The installed configuration exposes its own dock, monitor, font/colour and content-following policies.

For Vision this strengthens a layered fallback strategy:

- captured raster remains the universal baseline;
- the normal GPU renderer should improve geometric/image reconstruction;
- targeted semantic text enhancement may be added where reliable;
- a separate clean-text view can remain an optional accessibility fallback.

There is no evidence that all application text should be semantically re-rendered in the main magnified scene.

## xFont / renderer conclusion

Hands-on Word evidence materially narrows the renderer decision:

- at **2x**, ZoomText xFont was judged smooth, natural and visually strong;
- at **4x**, edges remained smooth but glyph shapes developed local bulges/deformations;
- phone photos at 4x show ZoomText as crisper than current Vision, while current Vision preserves glyph geometry comparatively well but is visibly softer.

This closes the earlier binary architecture question. Vision should **not** treat xFont-like semantic re-rendering as the default architecture. It should target:

1. materially better raster/GPU reconstruction and sharpening;
2. ZoomText-class perceived quality around the common 2x-3x range;
3. preservation of glyph geometry at higher zoom;
4. targeted semantic enhancement only where evidence justifies the compatibility cost.

A direct Vision-vs-ZoomText 2x user comparison remains useful as a release-quality benchmark, but it is no longer a prerequisite for the Opus architecture review.

## Scope to take into Opus

### First-product core

- reliable magnification and rendering;
- pointer/caret/focus tracking with predictable viewport policy;
- deliberate orientation layer: pointer, caret and focus visibility aids;
- fast context recovery: persistent Context + Detail, View Locator and exact temporary 1x/return;
- coherent 2-4 monitor model with per-view zoom/visual state;
- explicit monitor-crossing/active-view policy;
- simple colour/contrast/tint controls;
- robust Office/browser/Windows compatibility;
- persisted settings, install/update/diagnostics and contextual help;
- text quality good enough that it is not a competitive disadvantage at normal working magnifications.

### Preserve architecture seams, but do not require for launch

- one single-monitor contextual/lens/fixed view;
- Freeze/Hooked-Area-style pinned reference regions;
- Tethered-style dynamic context relocation;
- simple application-scoped settings;
- clone/standard-view collaboration;
- presentation mode;
- optional clean-text view.

### Defer unless user/dealer evidence promotes them

- span;
- large pointer/colour/highlight catalogues and editors;
- deep Situation Settings complexity;
- Reader/AppReader/OCR as a major product pillar;
- touch;
- camera/whiteboard;
- broad speech/screen-reader/Braille functionality.

## Evidence boundary and remaining gaps

The comprehensive ZoomText feature surface is now sufficient for pre-Opus review. Remaining uncertainties are bounded:

1. direct user preference between Vision and ZoomText at matched **2x** remains useful for a later release-quality target;
2. real-task value of Tethered View and Freeze-style regions should be user-tested before implementation;
3. physical 3/4-monitor behaviour still needs later hardware validation;
4. detailed compatibility of semantic text enhancement across applications is intentionally unresolved because no universal semantic path is currently recommended.

None of these needs to block the independent architecture/product review.

## Bottom line

ZoomText reinforces the same strategic direction as SuperNova but adds two particularly important challenges:

- **multi-monitor behaviour needs an explicit ownership/transfer policy**, not just independent output objects;
- **text quality should be solved as a layered quality problem**, not as a choice between raw raster scaling and an all-in semantic renderer.

The appropriate first-product ambition is therefore not feature parity. It is a smaller system with deep quality in magnification, orientation, context preservation, monitor behaviour, compatibility and recovery.
