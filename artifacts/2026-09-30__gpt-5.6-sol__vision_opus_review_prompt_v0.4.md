## Project

Vision is a Windows low-vision magnification application. It should ultimately work on ordinary Windows systems with **2, 3 or 4 active monitors**. Doxa is a later qualified hardware configuration, not a separate Vision architecture.

The intended strategy is **not** ZoomText/SuperNova feature parity. The current thesis is a smaller product with deep quality in magnification, orientation, context preservation, predictable multi-monitor behaviour, compatibility and recovery.

## Fixed programme decisions for this review

- Vision is hardware-agnostic and should support normal Windows 2/3/4-monitor systems.
- Doxa Installer/hardware work is separate and currently waits for real hardware evidence.
- Broader non-low-vision Doxa concepts are parked.
- Full screen-reader/Braille parity is outside the first-product boundary unless you find evidence that this makes the proposed product commercially incoherent.
- English ships first; localisation readiness should precede large UI growth.
- Clean-room constraints apply: public documentation and legitimate black-box behaviour may inform requirements, but no proprietary implementation inference or copying.
- Feature parity is not the target.
- Pricing strategy is deliberately postponed.
- Do not implement the proposed architecture during this review.


## Current evidence boundary

The current two-screen Vision alpha is real and tested. It already has:

- WGC capture and D3D11 presentation;
- pointer, caret and keyboard-focus evidence;
- POI arbitration and viewport policy;
- Context + Detail;
- View Locator;
- 1x/1.5x/2x/3x/4x and exact temporary 1x/return;
- basic pointer/caret/focus highlights;
- simple colour modes;
- persisted screen roles/settings;
- install/update/diagnostics;
- native Settings, Help / Ask Vision;
- repeatable two-screen acceptance/regression tooling.

The runtime is still essentially **one physical source -> one capture/render relationship -> one Detail output**, plus an optional unmanaged Reference display. Enumerating N monitors is not yet an N-view architecture.

The incumbent research stage is now complete enough for this review:

- SuperNova Magnifier 25.05 received a broad manual/menu/hands-on assessment;
- ZoomText 2026 received a broad manual/installed-state assessment;
- orientation aids were promoted from polish to first-product core;
- incumbent multi-monitor evidence introduced an explicit active-view/ownership question;
- ZoomText Tethered View clarified a dynamic context-relocation concept distinct from frozen reference;
- ZoomText Live Text View clarified a clean-text fallback role;
- hands-on Word comparison showed ZoomText xFont strong at 2x, crisper than current Vision at 4x, but with visible glyph-shape distortions at 4x;
- therefore universal semantic text re-rendering is **not** currently justified as the default renderer architecture.

Still unresolved:

- physical 3/4-monitor performance and usability;
- final monitor identity/recovery strategy, especially identical panels;
- cross-adapter/USB-display behaviour;
- user preference for active-view ownership versus more independent view following;
- matched Vision-vs-ZoomText 2x perceived quality as a release-quality benchmark;
- real-task value of pinned/frozen and Tethered-style workflows;
- broad workplace application compatibility.

Do not automatically convert every unresolved item into a pre-refactor blocker. Decide which uncertainties materially affect architecture extraction now and which can remain staged validation gates.

## Proposals under review

The current internal proposal is:

1. keep WGC/D3D11 as the universal capture/render baseline;
2. generalise fixed Context/Detail runtime into explicit monitor/topology, capture-source and view-session responsibilities;
3. share expensive capture/evidence work where practical;
4. make state attributable per view/destination rather than globally;
5. preserve Context + Detail as the default two-monitor workflow, not the only possible workflow;
6. separate orientation-overlay policy from viewport-motion policy;
7. add an explicit active-view/monitor-crossing policy rather than allowing all views to respond independently to global evidence;
8. improve raster/GPU text reconstruction first, while preserving a seam for targeted semantic text enhancement or a clean-text fallback;
9. preserve schema/architecture seams for app-scoped settings, pinned/context-relocated regions, clone/presentation and one contextual/lens/fixed view without implementing them during the extraction;
10. keep the first product deliberately narrower than incumbent breadth.

Your task is to decide which of these to keep, modify, reject or hold for more evidence.

## Questions to answer

### A. Product boundary and feature strategy

1. Is the focused magnifier-first product boundary coherent for low-vision users with useful functional vision? What evidence would falsify it?
2. Does the revised P0/P1/P2 scope in the incumbent synthesis prioritise the right problems? Identify overvalued, undervalued and missing capabilities.
3. Should Context + Detail remain the default differentiating workflow, become merely one preset, or be reconsidered?
4. Does a one-monitor Vision need at least one contextual/lens/fixed mode in the first product, or can that remain a post-core seam?
5. What is the smallest orientation preset system that is credible without recreating incumbent customisation complexity?
6. Which incumbent capabilities are likely to be dealer/assessor table stakes despite being outside everyday core use?

### B. 2-4 monitor architecture and interaction

7. Critique the proposed separation into monitor/topology service, CaptureSource, shared evidence sampling and per-output ViewSession. Is it the minimum clean model, over-abstracted, or missing a responsibility?
8. Should there be an explicit active-view/ownership controller above ViewSessions? Compare this with allowing each ViewSession to independently consume shared evidence.
9. How should evidence be routed so a pointer/caret/focus event cannot move the wrong view while still avoiding duplicate expensive UIA/Win32 sampling?
10. What is the safest incremental extraction from the current CaptureRunner-style coupling while preserving the validated two-screen behaviour after each slice?
11. For multiple views, should D3D11 device/capture resources be shared or isolated per view? Address hybrid/multi-adapter machines, WGC interop, failure isolation and fan-out cost.
12. Is same-monitor magnification robust enough to be first-class alongside cross-monitor magnification?
13. What monitor identity/topology model is appropriate across reboot, docking, port changes, hot-plug, mixed DPI and identical displays?
14. What is the minimum versioned workspace schema that expresses 2/3/4-monitor roles, source bindings, per-view visual/follow state and active-view policy without prematurely encoding Span/Clone/Presentation as special cases?


### C. Tracking, renderer quality and compatibility

15. Evaluate the combined monitor-boundary hypotheses: pointer-leave hold, optional resistance/cues, explicit monitor switching, and transferable active-view ownership. Which mechanisms belong in the architecture versus later UX experimentation?
16. Does the new xFont evidence justify the staged renderer hypothesis: WGC/raster baseline -> improved GPU reconstruction/sharpening -> targeted semantic enhancement only where justified -> optional clean-text fallback?
17. What text-quality experiments must precede renderer implementation, and which can safely occur after the multi-view architecture extraction?
18. What application compatibility matrix and regression strategy are necessary before Vision can credibly claim workplace usefulness?
19. How should pointer/caret/focus visibility state be represented so overlays remain independent from follow/motion policy and can vary per view?

### D. Context, settings and product engineering

20. Should app-scoped overrides be represented in the first versioned workspace/settings schema even if their user-facing UI is deferred?
21. What minimal abstraction, if any, should be preserved for future frozen/pinned regions and Tethered-style dynamic context relocation?
22. Should Live-Text-style clean text be represented as a future view type, an accessibility service, or deliberately left undefined until user evidence exists?
23. Should localisation readiness happen before, during or after architecture extraction? Is the proposed lightweight string-key/resource layer enough for the current Win32 UI?
24. Which current technical debts become disproportionately expensive once the product has multiple views, more settings and localisation?

### E. Implementation readiness and commercial implications

25. Which **smallest** remaining experiments must happen before architecture extraction begins? Rank them by decision value and do not promote later validation work into blockers without cause.
26. Which experiments should explicitly wait until after the architecture is generalised?
27. Does the smaller product boundary genuinely reduce lifetime support burden, or are Windows/app compatibility obligations still close to incumbent complexity?
28. Which capabilities matter commercially because they reduce dealer support, training or workplace deployment friction even if they are not daily-user features?
29. What evidence should be obtained from dealers/assessors before pricing/route-to-market work begins?
30. What is the strongest plausible entry wedge for Vision, and what technical/product evidence would falsify it?
