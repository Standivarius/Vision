# Vision owner Windows Magnifier comparison checkpoint v0.1

**Date:** 2026-10-01
**Status:** owner/debug session complete enough to inform protocol and roadmap; not a substitute for low-vision-user evidence.

## Environment

- Host: MARIUS-DELL
- Windows extended two-display desktop
- Microsoft Word synthetic task document
- comparison magnification: 4x
- Windows Magnifier follow settings verified: Keyboard focus ON, Text cursor ON
- Vision comparator: current two-monitor Context + Detail build

## Findings

### Windows Magnifier Full screen

At 2x/3x/4x the owner observed one magnified extended desktop spanning both physical displays.

This did not preserve the expected independent two-monitor roles. Word and Chrome became parts of one magnified workspace rather than one normal Context display plus one dedicated Detail display.

### Windows Magnifier Lens

Lens preserved the rest of the desktop and allowed the other physical monitor to remain normally usable.

However, with Word focused, mouse moved away, and both Keyboard focus and Text cursor follow settings verified ON, Lens did not return to/follow the Word insertion caret while typing in the observed task.

Treat this as a current Word/Lens compatibility/usability finding on this Windows build, not as a universal claim about every Magnifier/application combination.

### Windows Magnifier Docked

Docked followed the Word insertion caret.

Physical-photo evidence clarified its geometry: the magnified content is a full-width band attached to the top edge of the physical display. The normal application desktop is reduced/pushed down beneath it. The separate floating Magnifier toolbar is only a controller.

Therefore Docked is best modelled as reserved desktop area / screen partitioning, not as a floating rectangular magnifier window.

The owner judged this layout unsuitable for the intended dual-monitor workflow.

### Vision 4x

With Windows Magnifier fully off:

- one physical display remained a complete normal 1x Context workspace;
- the other physical display showed an independent full-screen 4x Detail;
- Word caret following worked correctly while Word was on the configured Context/source monitor;
- no application workspace was consumed by a docked strip.

When Word was moved off the Context/source monitor onto the Detail/output monitor, Vision did not follow it. Repository inspection confirmed this matches current implementation: pointer/caret/focus evidence is filtered to the configured source rectangle.

This is not a Word tracking defect. It exposes the difference between:
- current two-screen Context -> Detail behaviour; and
- the planned multi-source/shared-Detail active-view/crossing policy for configurations with more than one source-eligible workspace.

## Product interpretation

The owner/debug session supports the already-researched product direction rather than reopening it:

- Context + Detail remains a meaningful differentiating default;
- Windows Magnifier's three native views make different trade-offs and do not reproduce the same two-monitor workflow in the observed setup;
- Vision's current fixed-source two-screen behaviour is coherent;
- active-source/view ownership and monitor-crossing policy remains P0 first-product work for generic multi-source configurations.
