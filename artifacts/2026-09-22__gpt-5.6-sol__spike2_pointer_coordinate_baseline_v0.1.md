Can Visual establish a reliable, explicitly modeled coordinate foundation for pointer-driven behavior across a mixed-DPI Windows multi-monitor desktop?

## Coordinate component

Candidate reusable model:

`lab/prototypes/spike2_pointer_coordinate_truth/src/coordinate_model.h`

It explicitly distinguishes:

- virtual-desktop screen point;
- monitor rectangle;
- monitor-local point;
- normalized monitor point.

The model uses half-open Win32 rectangle semantics and does not assume monitor origins are non-negative.

## DPI conclusion

An earlier Spike 1 PowerShell/RDP-oriented collector reported the laptop as 1280x720. Under a PMv2-aware native process the same display is consistently exposed as 1920x1080, and the three native geometry sources agree.

The earlier 1280x720 observation should therefore be treated as DPI-virtualized collection evidence, not as the canonical coordinate space for Visual.

For per-monitor DPI, this spike currently treats `GetDpiForWindow` on a hidden PMv2 top-level window created on each monitor as canonical evidence.

The legacy comparison values expose an important discrepancy on DISPLAY1:

- `GetDpiForWindow`: 144 DPI -> 150%
- `GetDpiForMonitor`: 144 DPI
- `GetScaleFactorForMonitor`: 140%

Visual should not build coordinate conversion logic around the legacy scale-factor API.

## Interpretation

The baseline hypothesis is supported for the current physical two-display mixed-DPI topology:

- PMv2 pointer coordinates are stable;
- pointer-to-monitor resolution is correct;
- monitor-local and normalized transformations are internally consistent;
- mixed 150%/100% DPI does not introduce unexplained pointer jumps;
- the shared coordinate arithmetic handles negative/vertical layouts synthetically.

## Remaining Spike 2 evidence

Before treating the coordinate model as fully characterized, perform targeted physical topology variants when convenient:

1. external monitor left of laptop, producing negative X;
2. external monitor above/below laptop;
3. primary-display swap;
4. optionally another mixed-resolution/scaling combination;
5. later the four-screen Doxa topology.

These variants should not block beginning the next independent capability spike, because the baseline mixed-DPI cross-monitor coordinate model is now strong enough to build against while retaining topology variants as explicit follow-up validation.
